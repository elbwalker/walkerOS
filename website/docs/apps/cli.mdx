# walkerOS CLI

The walkerOS CLI (`@walkeros/cli`) is a command-line tool for building, testing, and running event collection flows. It handles the complete workflow from configuration to deployment. It bundles flows into optimized JavaScript, testing with simulated events, and running collection servers locally or in Docker.

## Installation

### Global Installation (Recommended)

Install globally to use the `walkeros` command anywhere:

<CodeSnippet
  code={`npm install -g @walkeros/cli

# Verify installation
walkeros --version`}
  language="bash"
/>

### Local Installation

Install in your project for team consistency:

<CodeSnippet
  code={`npm install --save-dev @walkeros/cli

# Use with npx
npx walkeros --version`}
  language="bash"
/>

## Commands overview

| Command | Purpose | Use Case |
|---------|---------|----------|
| `bundle` | Build production-ready bundle from flow config | Create deployable JavaScript from configuration |
| `push` | Execute event with real API calls (or `--simulate` for mocked) | Testing and production validation |
| `setup` | Run the optional `setup()` lifecycle on one component | Provision external resources (BigQuery datasets, Pub/Sub topics, SQLite tables, webhook registrations) |
| `validate` | Validate events, flows, mappings, contracts, or entries | Check configuration before bundling |
| `cache` | Manage CLI package and build caches | Clear stale caches, view cache statistics |
| `auth` | Authentication and identity | Log in, log out, check identity |
| `projects` | Manage walkerOS projects | Create, list, update, delete projects |
| `flows` | Manage walkerOS flows | Create, list, update, delete, duplicate flows |
| `deploy` | Create and manage deployments | Deploy flows to walkerOS cloud or self-hosted |
| `previews` | Manage preview bundles | Test flow changes on live sites before deploying |
| `observe` | Open an Observe session on a flow | Watch a running flow's live events from the terminal |

The `push` command accepts either a config JSON or a pre-built bundle as input.

## Configuration types

The CLI uses types from `@walkeros/core`:

- **`Flow.Json`** - Root config file format (`version`, `flows`)
- **`Flow`** - Single flow (has `config`, `sources`, `destinations`, `transformers`, `collector`)
- **`Flow.Config`** - Per-flow config block (`platform`, `url`, `settings`, `bundle`)
- **`Collector.InitConfig`** - Runtime type passed to `startFlow()`

The CLI transforms `Flow.Json` → `Flow` (per flow) → bundled code that uses `Collector.InitConfig` at runtime.

## Packages and overrides

Build-time concerns live under each flow's `config.bundle` block. Three fields are supported:

- **`packages`**: the list of npm packages (or local paths) the bundler should install for this flow. Pacote downloads them based on this list. You do **not** need to run `npm install` yourself for step packages; the CLI handles it transparently.
- **`overrides`**: pin transitive dependency versions, matching npm's `overrides` semantics. Useful when an upstream package declares an overly narrow version range that conflicts with a newer transitive version in the same tree.
- **`traceInclude`** (server flows only): an escape hatch for the file tracer. See below.

<CodeSnippet
  code={`"flows": {
  "default": {
    "config": {
      "platform": "server",
      "bundle": {
        "packages": {
          "@walkeros/collector": {}
        },
        "overrides": {
          "@amplitude/analytics-types": "2.11.1"
        }
      }
    }
  }
}`}
  language="json"
/>

### Server bundles use nft tracing

Server flows (`platform: "server"`) are traced automatically with [`@vercel/nft`](https://github.com/vercel/nft). The bundler externalizes every step package, then nft walks the entry to figure out which files are actually reachable at runtime, and copies only those files into `dist/node_modules/`. Native add-ons, `.proto` files, and `__dirname`-loaded assets are picked up.

There is no `walkerOS.bundle.external` annotation: nft figures out the externalization automatically.

After tracing, the bundler checks every package in `bundle.packages` that the bundle imports (a step's package, or a package exposed through `imports`). One missing from the trace fails the build (`nft-trace: resolved packages missing from trace: ...`). A declared package that the bundle does not import and no traced package pulls in (for example one a step package needs for its types only) is not in the bundle, and the build only warns:

```
Package @walkeros/server-core is declared in bundle.packages but nothing imports it; it is not in the bundle. Remove it from bundle.packages if unused.
```

### Escape hatch: `traceInclude`

If nft cannot statically reach a file (rare: dynamic `require(somePath)` constructed from a runtime variable, dynamically loaded data files), declare it explicitly with `flow.<name>.config.bundle.traceInclude`. Paths and globs are both supported (matched via picomatch). Paths resolve against the install root, not your project directory.

<CodeSnippet
  code={`"flows": {
  "default": {
    "config": {
      "platform": "server",
      "bundle": {
        "packages": { "@walkeros/server-destination-gcp": {} },
        "traceInclude": [
          "node_modules/some-pkg/data/*.json",
          "node_modules/another-pkg/lib/runtime-loaded.js"
        ]
      }
    }
  }
}`}
  language="json"
/>

### Range conflict resolution

When two transitive consumers declare incompatible ranges for the same dependency (e.g., `arrify@^3.0.0` from one package, `arrify@^2.0.0` from another), the bundler now resolves the chosen range to a concrete version via the npm registry and nests any non-satisfying spec under its consumer's `node_modules/`. This kills classes of upstream chaos (like `arrify is not a function` from `@google-cloud/common`) before they can reach runtime. After install, a defense-in-depth check warns when any installed package's declared deps don't match what's reachable on its resolution path; if you see those warnings, add an `overrides` entry to your flow's `config.bundle.overrides` to pin the offending dep. If the npm registry is unreachable during validation, set `BUNDLER_STRICT_RANGES=0` to bypass strict validation with a warning instead of failing the build.

### Schema version

The flow.json schema stays at `version: 4`. Build-time fields live under `flow.<name>.config.bundle.{packages, overrides, traceInclude}`. The `flow.<name>.config.bundle.external` sub-field is no longer supported in @walkeros/cli@4.x.

## Package imports

### Implicit collector

The collector is added automatically. To pin a specific version (recommended for production), add the collector explicitly:

<CodeSnippet
  code={`"packages": {
  "@walkeros/collector": { "version": "1.0.0" },
  "@walkeros/web-source-browser": {},
  "@walkeros/destination-demo": {}
}`}
  language="json"
/>

### Default exports (sources & destinations)

Sources and destinations automatically use their **default export** - no `imports` needed:

<CodeSnippet
  code={`"packages": {
  "@walkeros/web-source-browser": {},        // Uses default export
  "@walkeros/destination-demo": {}           // Uses default export
}`}
  language="json"
/>

### Utility imports

Use `imports` when you need specific utility functions from a package:

<CodeSnippet
  code={`"packages": {
  "@walkeros/core": { "imports": ["getId", "clone"] },     // Optional utilities
  "@walkeros/web-source-browser": {
    "imports": ["createTagger"]                            // Additional utility
  }
}`}
  language="json"
/>

### Named-export selection with `import`

For packages without a default export, or to pick a specific named export, set `import` on the step alongside `package`. The bundler adds the name to the `imports` list automatically.

<CodeSnippet
  code={`"sources": {
  "custom": {
    "package": "@my/custom-package",
    "import": "namedExport"
  }
}`}
  language="json"
/>

The legacy `code: "namedExport"` form is no longer accepted. Validation raises `OBSOLETE_CODE_STRING` with a rename hint pointing to `import`.

## Local packages

By default, the CLI downloads packages from npm. For development or testing unpublished packages, you can use local packages instead by specifying a `path` property.

### Configuration

Add a `path` property to any package to use a local directory instead of npm:

<CodeSnippet
  code={`{
  "packages": {
    "@my/custom-destination": {
      "path": "./my-custom-destination"
    }
  }
}`}
  language="json"
/>

### Resolution Rules

- **`path` takes precedence** - When both `path` and `version` are specified, `path` is used
- **Relative paths** - Resolved relative to the config file's directory
- **Absolute paths** - Used as-is
- **dist folder** - If a `dist/` folder exists, it's used; otherwise the package root is used

### Dependency Resolution

When a local package has dependencies on other packages that are also specified with local paths, the CLI will use the local versions for those dependencies too. This prevents npm versions from overwriting your local packages.

<CodeSnippet
  code={`{
  "packages": {
    "@walkeros/core": {
      "path": "../packages/core"
    },
    "@walkeros/collector": {
      "path": "../packages/collector"
    }
  }
}`}
  language="json"
/>

In this example, even though `@walkeros/collector` depends on `@walkeros/core`, the local version of core will be used (not downloaded from npm). This is essential when testing changes across multiple interdependent packages.

### Use Cases

**Development of custom packages:**
<CodeSnippet
  code={`{
  "packages": {
    "@my-org/destination-custom": {
      "path": "../my-destination"
    }
  }
}`}
  language="json"
/>

**Testing local changes to walkerOS packages:**
<CodeSnippet
  code={`{
  "packages": {
    "@walkeros/collector": {
      "path": "../../packages/collector"
    }
  }
}`}
  language="json"
/>

When ready for production, simply remove the `path` property to use the published npm version.

## Bundle command

The `bundle` command builds production-ready JavaScript bundles from flow configurations.

### Use Case

You've defined your sources, destinations, and transformations in a flow configuration file. Now you need to:
- Download the required npm packages
- Bundle everything into a single optimized JavaScript file
- Deploy it to production (Docker, Cloud Run, serverless functions)

The bundle command handles all of this.

### Basic Usage

<CodeSnippet
  code={`walkeros bundle flow.json`}
  language="bash"
/>

This writes the optimized bundle to stdout (web flows only). Use `-o` to write to a file or directory (e.g., `-o ./dist/walker.js` for web, `-o ./dist/` for server, which produces `dist/{flow.mjs, package.json, node_modules/}`). For server flows you can also write a `.tar.gz`/`.tgz` archive (e.g., `-o ./flow.tar.gz`), which packs the server bundle directory (`flow.mjs`, `package.json`, `node_modules/`) into a single gzip file. Web single-file bundles do not support archive output.

### Step-by-Step Guide

**1. Create a flow configuration**

Create `server-collect.json`:

<CodeSnippet
  code={`{
  "version": 4,
  "flows": {
    "default": {
      "config": {
        "platform": "server",
        "bundle": {
          "packages": {
            "@walkeros/server-source-express": {},
            "@walkeros/destination-demo": {}
          }
        }
      },
      "sources": {
        "http": {
          "package": "@walkeros/server-source-express",
          "config": {
            "settings": {
              "path": "/collect",
              "port": 8080,
              "cors": true
            }
          }
        }
      },
      "destinations": {
        "console": {
          "package": "@walkeros/destination-demo",
          "config": {
            "settings": {
              "name": "Event Logger",
              "values": ["name", "data.title", "timestamp"]
            }
          }
        }
      },
      "collector": { "run": true }
    }
  }
}`}
  language="json"
/>

**2. Bundle the flow**

<CodeSnippet
  code={`walkeros bundle server-collect.json --stats`}
  language="bash"
/>

Output:
```
📦 Downloading packages from npm...
✓ @walkeros/collector@latest
✓ @walkeros/server-source-express@latest
✓ @walkeros/destination-demo@latest

🔨 Bundling...
✓ Bundle created: ./dist/flow.mjs

📊 Bundle Statistics:
   Size: 45.2 KB (minified)
   Packages: 3
   Format: ESM
```

**3. Review the bundle**

<CodeSnippet
  code={`ls -lh dist/
# -rw-r--r--  1 user  staff   45K  flow.mjs
# -rw-r--r--  1 user  staff  152B  package.json
# drwxr-xr-x 12 user  staff  384B  node_modules

file dist/flow.mjs
# dist/flow.mjs: JavaScript source, UTF-8 Unicode text`}
  language="bash"
/>

The bundle is now ready to deploy!

### Options

<CodeSnippet
  code={`walkeros bundle <config-file> [options]`}
  language="bash"
/>

| Option | Description |
|--------|-------------|
| `-o, --output <path>` | Write bundle to file, directory, or presigned URL |
| `-f, --flow <name>` | Build specific flow (for multi-flow configs) |
| `--all` | Build all flows |
| `--stats` | Show bundle statistics |
| `--json` | Output statistics as JSON (for CI/CD) |
| `--no-cache` | Skip package cache, download fresh |
| `--release <id>` | Config release id, stamped on `event.source.release` |
| `--manifest [source]` | Build from a manifest, see [manifest builds](#manifest-builds---manifest) |
| `-v, --verbose` | Detailed logging |
| `-s, --silent` | Suppress output |

When `--output` is a URL (e.g., a presigned S3 URL), the CLI bundles to a temp file and uploads via HTTP PUT. This is used by the walkerOS cloud service for remote builds.

For server flows, `-o` resolves to a directory: `dist/{flow.mjs, package.json, node_modules/}`. When `-o` ends in `.tar.gz` or `.tgz`, that same directory is packed into a single gzip archive instead (server flows only). For multi-flow `--all`, each flow gets its own subdirectory: `dist/<flowName>/...`.

  code={`# Bundle development flow

# Bundle production with stats

# Bundle all flows
walkeros bundle config.json --all`}
  language="bash"
/>

### Build-time values (`config.bundle.env`)

A web flow resolves its `$env.NAME` references when it is bundled and inlines
the values into `walker.js`. The flow declares those values under
`config.bundle.env`, so the same config bundles the same way wherever it is
built:

<CodeSnippet
  code={`"flows": {
  "default": {
    "config": {
      "platform": "web",
      "bundle": {
        "env": { "GA4_MEASUREMENT_ID": "G-XXXXXXX" }
      }
    }
  }
}`}
  language="json"
/>

- Values must be literal strings. A reference inside one (`$env.`, `$var.`,
  `$secret.`, `$flow.`, `$contract.`, `$code:`) is refused.
- A local `walkeros bundle` layers `config.bundle.env` over your shell
  environment, declared values winning. A hosted build and a
  [manifest build](#manifest-builds---manifest) use the declared values alone, so a
  missing name fails the build instead of reading the build machine's
  environment.
- A `$flow.<sibling>` reference resolves against the entry flow's
  `config.bundle.env`, not the sibling's own.
- Everything declared here ends up in a public bundle. Never put a secret in
  it; web flows cannot hold secrets.

Server flows ignore `config.bundle.env`: their `$env` references are read at
runtime from the process environment of the runtime.

### Include folders

The root `include` field lists folders the bundler copies next to a server bundle, for files the flow reads at runtime (see [serving files](/docs/apps/runtime#serving-files)). Without `include`, a `shared/` folder next to the config is copied when it exists. Including the output directory itself is refused as a circular copy. A server build served from the build cache copies them too, so a clean output directory gets the same files as a fresh build.

`include` applies to server builds only. A browser bundle is served on its own and cannot read local folders, so a web build copies nothing and logs once:

```
include is ignored for web builds: a browser bundle cannot read local folders.
```

For the same reason a [manifest build](#manifest-builds---manifest) of a web flow accepts `include` and ignores it; only a server flow's `include` is refused there.

### Package specs

Every package the bundler installs must come from the npm registry: a
version (`1.2.3`), a range (`^1.2.0`) or a tag (`latest`). This applies to
`config.bundle.packages`, to `config.bundle.overrides` values, and to the
dependencies those packages pull in. Git, `github:`, `file:`, `link:` and
tarball-URL specs are refused before any download, because fetching them can
run code. An optional transitive dependency with such a spec is skipped with a
warning. Install scripts of downloaded packages do not run. For local
development, use a [local package](#local-packages) `path` instead.

### Manifest builds (`--manifest`)

`walkeros bundle --manifest <url-or-path>` builds from a JSON manifest instead
of a config file. It is the contract a build orchestrator (a CI job, a hosted
build job, your own script) uses to drive the CLI: the manifest names the flow,
the artifacts to build and a presigned PUT URL for each; the CLI builds them,
uploads each one, then uploads a result. A bare `--manifest` reads the
location from `BUILD_MANIFEST_URL`. Only `--json`, `--verbose` and `--silent`
combine with it.

| Field | Description |
|---|---|
| `version` | `1` |
| `toolchain` | The exact `@walkeros/cli` version. Any other version refuses the build |
| `flowConfig` | The `flow.json` content. Required when any bundle artifact is requested |
| `flowName` | Flow to build in a multi-flow config |
| `buildEnv` | Base values for web `$env`, beneath `config.bundle.env`. Never the CLI process's own environment |
| `artifacts[]` | At least one. Each has a unique `outputName` (a bare file name), a `putUrl`, and optional `contentType` and `headers`. A bundle artifact sets `target` (`cdn`, `cdn-skeleton`, `runner`, `simulate` or `push`); a wrap artifact sets `target: "wrap"`, `platform` and `skeleton` |
| `resultPutUrl` | Presigned PUT URL for the result JSON |

The result is `{ ok, toolchain, artifacts: [{ target, outputName, bytes, sha256 }], error? }`,
where `error` carries a `code`, a `message` and the `outputName` being built.
Error codes: `INVALID_MANIFEST`, `TOOLCHAIN_MISMATCH`, `INVALID_CONFIG`,
`MISSING_BUILD_ENV`, `WEB_SECRET_REF`, `UNSUPPORTED_PACKAGE_SPEC`,
`LOCAL_PATH_NOT_ALLOWED`, `BUILD_FAILED`, `UPLOAD_FAILED`.

Unknown top-level fields are ignored, so an orchestrator can keep its own
bookkeeping in the manifest. Artifact entries are strict. A manifest build
refuses every local filesystem input (local step packages, a package `path`,
`bundle.traceInclude`, a server flow's `include`) with `LOCAL_PATH_NOT_ALLOWED`. The Zod
schemas are exported from `@walkeros/cli` as `BuildManifestSchema` and
`BuildResultSchema`, the codes as `BUILD_ERROR_CODES`.

## Push command

The `push` command executes your flow with a real event. By default it makes actual API calls to your configured destinations. Use `--simulate` to mock specific steps for safe testing. It accepts either a config JSON (which gets bundled) or a pre-built bundle.

### Use Case

You want to:
- Test event processing with mocked destinations (`--simulate`)
- Test with real third-party APIs (GA4, Meta, BigQuery, etc.)
- Verify production credentials and endpoints work
- Debug actual API responses and errors
- Perform integration testing before deployment
- Execute a pre-built bundle without rebuilding

Push handles both safe local testing (with `--simulate`) and real integration testing.

### Basic Usage

<CodeSnippet
  code={`# With config JSON (auto-bundled)
walkeros push flow.json --event '{"name":"page view","data":{"title":"Home"}}'

# With pre-built bundle
walkeros push dist/flow.mjs --event '{"name":"page view"}'`}
  language="bash"
/>

### Step-by-Step Guide

**1. Create a flow configuration**

Create `api-flow.json` with a destination that makes real HTTP calls:

<CodeSnippet
  code={`{
  "version": 4,
  "flows": {
    "default": {
      "config": {
        "platform": "server",
        "bundle": {
          "packages": {
            "@walkeros/web-destination-api": {}
          }
        }
      },
      "destinations": {
        "api": {
          "package": "@walkeros/web-destination-api",
          "config": {
            "settings": {
              "url": "https://your-endpoint.com/events",
              "method": "POST"
            }
          }
        }
      },
      "collector": { "run": true }
    }
  }
}`}
  language="json"
/>

**2. Create an event file**

Create `event.json`:

<CodeSnippet
  code={`{
  "name": "order complete",
  "data": {
    "id": "ORD-12345",
    "total": 299.99,
    "currency": "USD"
  },
  "user": {
    "id": "user_abc123"
  }
}`}
  language="json"
/>

**3. Push the event**

<CodeSnippet
  code={`walkeros push api-flow.json --event event.json --verbose`}
  language="bash"
/>

**4. Review the output**

```
📥 Loading event...
📦 Loading flow configuration...
🔨 Bundling flow configuration...
🖥️  Executing in server environment (Node.js)...
Pushing event: order complete
✅ Event pushed successfully
   Event ID: 1701234567890-abc12-1
   Entity: order
   Action: complete
   Duration: 1234ms
```

The event was sent to your real API endpoint!

### Options

<CodeSnippet
  code={`walkeros push <input> [options]`}
  language="bash"
/>

| Option | Description |
|--------|-------------|
| `-e, --event <source>` | **Required.** Event to push (JSON string, file path, or URL) |
| `-f, --flow <name>` | Flow name (for multi-flow configs) |
| `-p, --platform <platform>` | Platform override (`web` or `server`) |
| `--simulate <step>` | Simulate a step (repeatable). Mocks the step's push, captures result. Use `source.NAME`, `transformer.NAME`, `destination.NAME`, or `collector.NAME` (for example `collector.default`). A transformer runs through its own `before` and `next`; the collector step runs the collector's enrichment and then `collector.next`, so it returns every copy that would reach the destinations (none when a `stop` drops the event). |
| `--ingest <source>` | Request context for the simulated step (JSON string, file path, or URL; must be a JSON object), for example `{"ip":"203.0.113.7","userAgent":"Mozilla/5.0"}`. Applies to `transformer.*`, `collector.*` and `destination.*` simulation only. |
| `--consent <source>` | Collector consent the simulated step starts from (JSON string, file path, or URL; a JSON object of booleans), for example `{"functional":true,"marketing":true}`. Applies to every simulated step, sources included; rejected for a real push. See [consent in simulate](#consent-in-simulate). |
| `--command <name>` | The simulated destination runs this collector command (`config`, `consent`, `user` or `run`) with the event as its data, instead of a push. `destination.*` simulation only. |
| `--page-url <url>` | Page URL of a simulated web source (absolute `http` or `https` URL). `source.*` simulation of a web flow only. Default: the input trigger's `options.url`, else `http://localhost`. |
| `--mock <step=value>` | Mock a step with a specific return value (repeatable). Use `destination.NAME=VALUE`, a chain member such as `destination.NAME.before.TRANSFORMER=VALUE`, or a member of the collector chain with `collector.next.TRANSFORMER=VALUE`. |
| `--snapshot <source>` | JS file to eval before execution. Sets global state (`window.dataLayer`, `process.env`, etc.). |
| `-o, --output <path>` | Write result to file |
| `--json` | Output results as JSON. For a real and a simulated push alike, stdout carries only the JSON document; logs go to stderr |
| `-v, --verbose` | Verbose output with debug information |
| `-s, --silent` | Suppress output (for CI/CD) |

### Input Types

The CLI auto-detects the input type by attempting to parse as JSON:
- **Config JSON** - Bundled and executed
- **Pre-built bundle** (`.js`/`.mjs`) - Executed directly

When using pre-built bundles, platform is detected from file extension:
- `.mjs` → server (ESM, Node.js)
- `.js` → web (IIFE, JSDOM)

Use `--platform` to override if extension doesn't match intended runtime.

**File path:**

| Mode | Flag | API Calls | Use Case |
|------|------|-----------|----------|

### Simulation output

A simulated destination runs with the mock env its package ships (`examples.env.push`), so the vendor SDK or HTTP call is recorded instead of sent. The output lists, per simulated step, the mapping rule that matched and every recorded vendor call:

<CodeSnippet

Each destination step prints `mapping: <entity action key>` when a rule matched, `mapping: none` when it pushed the event without a matching rule, or `mapping: none (skipped before mapping)` when nothing was sent, then one `call <fn>(<args>)` line per recorded call (arguments as compact JSON, cut at 300 characters) or `no calls`. When nothing was sent, a line before the calls says why:

- `pending: waits for consent (require)`: the destination has `require` and never started (it names the unmet `require` entries).
- `skipped: consent (requires marketing; granted functional)`: the destination started, but its consent check skipped the event. It names the consent the destination requires and what was granted (collector consent plus the event's own consent).

Source, transformer and collector steps print their recorded calls, then the events they pass on (`event <json>` or `no events`).

A source step also records the walker commands the source issues itself, as `elb` calls in the source's own call shape: a CMP source's `walker consent`, the session source's `user` and `session`. The collector's own commands (the starting consent, globals and custom of the flow, the final shutdown) and the wiring commands `on`, `hook` and `destination` are not recorded. Arguments are made printable (an `Error` becomes `{ name, message }`, a `Buffer` its UTF-8 text, `bigint` a string, `Map` and `Set` arrays, cycles `"[Circular]"`). Both text and JSON output pass through the same secret scrubbing the CLI logs use, so service account keys, private keys, `Authorization` headers, `access_token` parameters and credential fields show as `***`. The values of the secrets the flow references (every `$secret.NAME` that is set in the environment, 6 characters or longer) are masked as they are, also inside JSON strings. With `--json`, a number that prints a digits-only known value becomes the string `"***"`, so the document still parses. The destination itself still receives the real values.

A simulation and a real push of a flow config both route the flow's own logs through the same masking CLI logger (to stderr with `--json`), so the flow's debug lines appear only with `--verbose`. A real push of a prebuilt bundle keeps the bundle's own logger unless `--json` is set. The runtime masks the fetched secret values in its logs too (see [the runtime docs](/docs/apps/runtime#connecting-to-the-walkeros-app)).

**What starts in a simulation.** A destination simulation starts only its target destination: no source and no other destination initializes, so no other vendor script or SDK client is built. The flow's transformers still start, and a store whose package ships no mock env runs as configured (with `--verbose`: `Stores without a mock env run as configured: ...`). A source simulation starts only the simulated source, so a web source never adds the browser source's page view or a CMP decision of its own. The events it captures stop at the collector and reach no destination. A source whose package declares recorded calls (`examples.env.simulation`, for example the SQS and Pub/Sub pull sources) runs on its mock client, and those calls are listed like a destination's.

**No real vendor calls.** The guarantee covers destinations. When a package destination's export has no mock env, simulate stops before the flow starts (a step with inline `code` has no package and runs as given):

```

```

A multi-export package (for example `@walkeros/server-destination-gcp` with `destinationBigQuery` and `destinationPubSub`) keys its dev examples by export name, and simulate picks the entry for the step's `import`. A package version published before that convention is refused for a named export with `...: this package version predates export-keyed examples; use a version with exportExamples or a local path.`

**Request context with `--ingest`.** Destinations that read the request (client IP, user agent) get it from the ingest context, which an HTTP source fills in a running flow. Pass it with `--ingest` to see what those destinations send:

#### Consent in simulate

Three settings decide whether a destination receives an event. They are easy to mix up, and a simulation shows each one separately:

| Setting | Where | What it does | In a simulation |
|---|---|---|---|
| `require: ["consent"]` | Destination `config` | The destination stays pending (not initialized, events queued) until the collector has any consent state | Starts once `--consent` is passed. Without it: `pending: waits for consent (require)` |
| `consent: { marketing: true }` | Destination `config` | Each event is checked against the collector's consent plus the event's own consent; a denied event is skipped (or queued with `queue: true`) | Grant it with `--consent` or in the event's `consent`. Otherwise: `skipped: consent (...)` |
| `consent` on the event | The event (`-e`) | Consent of this one event, counted on top of the collector's consent | Part of the event you pass |
| `consent` in a source's settings | Source `config.settings` (for example the session source) | The source waits for that consent before it emits | A consent-gated source starts from `--consent`. Without it, it emits nothing |

`--consent` sets the collector consent the simulated step starts from. The flow starts with it (it is applied before the flow runs, as a `consent` command that only the simulated step hears), so a destination with `require: ["consent"]` starts, and its consent check sees the granted keys. A destination with Consent Mode enabled (`como`) records the resulting `gtag('consent','update',...)` call. For a source simulation it is the consent a consent-gated source finds when it starts; this starting consent is never recorded as one of the source's calls. Without `--consent` the simulation grants nothing. The value is a JSON object of booleans (otherwise: `--consent must be a JSON object of booleans`), given inline, as a file path or as a URL. `--consent` is rejected for a real push:

```
--consent sets the collector's starting consent for a simulation; a real push uses the flow's own consent.
```

## Setup command

The `setup` command runs the optional `setup()` lifecycle on a single component to provision external resources before traffic flows. Use it for one-time provisioning steps like creating a BigQuery dataset and table, declaring a Pub/Sub topic and subscription, creating SQLite tables, or registering a webhook with a third-party API.

For the conceptual overview of the lifecycle (when to implement `setup()` in a component, how it relates to the runtime hot path, and the operator separation rationale), see [Setup lifecycle](/docs/destinations/create-your-own#setup-lifecycle-optional).

### Use case

Setup is for the operator-time, "do this once before traffic" step that sits between writing config and accepting events:

- A BigQuery destination needs its dataset and table to exist with the right schema before rows can be streamed in.
- A Pub/Sub source needs a subscription against a topic before it can pull messages.
- A SQLite store needs its tables created before reads and writes work.
- A webhook integration needs to register its callback URL with the upstream service.

Setup is **explicit only**. It is never triggered by `push`, `simulate`, `deploy`, or the long-running runtime. You run it once when provisioning, then again only when external resources need to be re-provisioned (for example, after changing the table schema in config). The runtime never tries to "fix" missing resources on its own.

### Basic usage

<CodeSnippet
  code={`# Provision the BigQuery dataset and table for the destination named "bigquery"
walkeros setup destination.bigquery`}
  language="bash"
/>

### Target syntax

The target uses the same `<kind>.<name>` syntax as `walkeros push --simulate`. Valid kinds are `source`, `destination`, and `store`. Transformers are pure functions and have no setup.

| Target | Resolves to |
|--------|-------------|
| `destination.bigquery` | The destination named `bigquery` in the resolved flow |
| `source.events-in` | The source named `events-in` |
| `store.session` | The store named `session` |

### Package resolution

Setup resolves the component's package exactly like `walkeros bundle`: the version pinned in `config.bundle.packages` (or inline on the step as `"@scope/pkg@x.y.z"`, with the bundle pin winning on disagreement) is downloaded from the npm registry into a temporary tree and imported from there.

<CodeSnippet
  code={`{
  "config": {
    "platform": "server",
    "bundle": {
      "packages": {
        "@walkeros/server-destination-gcp": { "version": "4.4.0" }
      }
    }
  },
  "destinations": {
    "bigquery": {
      "package": "@walkeros/server-destination-gcp",
      "config": { "setup": true }
    }
  }
}`}
  language="json"
/>

What this means in practice:

- **Works from any install.** npx, devDependency, or global: no local `npm install` of the component package is needed or consulted.
- **Shared cache with bundle.** Exact version pins keep working offline once cached; `latest` and ranges re-resolve against the registry.
- **Local packages via `path`.** A `path` entry in `config.bundle.packages` is supported for local development; the target must be a built package directory (package.json plus dist output), since setup imports with Node at runtime.
- **No version drift with exact pins.** Setup and bundle resolve through the same pipeline and cache, so an exact version pin guarantees both act on the same package release and provisioning (for example a BigQuery schema) cannot drift from what the bundle writes. Mutable specifications (`latest`, ranges, `path` targets) can resolve differently between separate runs, so pin exact versions when drift matters.

### Options

<CodeSnippet
  code={`walkeros setup <target> [options]`}
  language="bash"
/>

| Option | Description |
|--------|-------------|
| `-c, --config <path>` | Flow config file (default: `./flow.json`) |
| `-f, --flow <name>` | Flow name for multi-flow configs |
| `--json` | Output as JSON (passed to the package's setup logger) |
| `-v, --verbose` | Verbose output |
| `-s, --silent` | Suppress output |

### What "skip" means

The framework narrates one of three reasons when nothing runs and exits successfully:

| Reason | Trigger |
|--------|---------|
| `no setup function` | The package does not export a `setup` function on its default export |
| `config.setup is false` | The flow config explicitly opts out with `"setup": false` |
| `config.setup is unset` | The flow config does not declare `setup` at all |

In all three cases the exit code is `0`. Setup is a single-purpose command, not a tiered status check.

### Result output

When the package's `setup()` returns a non-undefined value, the CLI emits it as JSON on stdout for `jq`-style scripting. This lets you script around what was provisioned:

<CodeSnippet
  code={`walkeros setup destination.bigquery --json | jq .datasetCreated`}
  language="bash"
/>

If the package returns nothing, no JSON is emitted; you only see the framework narration.

### Exit codes

| Code | Meaning |
|------|---------|
| 0 | Success or skip (any of the three skip reasons above) |
| non-zero | Failure (resolution error, missing default export, package threw) |

### IAM note

Setup typically needs higher permissions than runtime push: "create dataset" or "create subscription" vs "write rows" or "pull messages". Operators commonly run setup with a separate service account, or different credentials, than the runtime uses. Plan your IAM accordingly: grant the runtime only what it needs to push, and grant setup the broader provisioning scope.

# Same but pointing to a specific flow in a multi-flow config.
walkeros setup destination.bigquery --flow analytics

# Custom config path.
walkeros setup destination.bigquery --config ./flows/prod.json

# Pipe the structured result to jq.

  language="bash"

## Validate command

The `validate` command checks the structure and correctness of events, flow configurations, mapping configurations, contracts, or individual flow entries before bundling or deployment.

### Use case

Before bundling or deploying your flow, you want to:
- Catch configuration errors early
- Verify event structure follows walkerOS conventions
- Check mapping patterns are valid
- Validate contracts follow the named-entry shape, with entity-action schemas nested under `events`
- Validate a specific destination, source, or transformer entry against its package's published JSON Schema
- Integrate validation into CI/CD pipelines

Validate gives you fast feedback without the overhead of bundling.

### Basic usage

<CodeSnippet
  code={`# Validate a flow configuration (schema, references, cross-step examples)
walkeros validate flow.json

# Validate an event structure
walkeros validate event.json --type event

# Validate a mapping configuration
walkeros validate mapping.json --type mapping

# Validate a contract
walkeros validate contract.json --type contract

# Validate a specific entry against its package schema
walkeros validate flow.json --path destinations.snowplow`}
  language="bash"
/>

### Validation types

The `--type` option accepts four validation types. Default is `flow`:

| Type | What it validates |
|------|-------------------|
| `event` | Event structure: `name` field exists, follows "entity action" format with space, valid data types |
| `flow` (default) | Flow.Json config: schema, references, packages, cross-step example compatibility, and the examples of `@walkeros/transformer-validate` steps against their linked contracts |
| `mapping` | Mapping rules: event patterns use "entity action" or wildcard format, rule structures are valid |
| `contract` | Contract structure: named entries with optional `extend`, `tagging`, `description`, `events`, and `schema` fields |

Use `--path` for entry validation against package schemas (e.g., `--path destinations.snowplow`).

### Step-by-step guide

**1. Validate a flow configuration**

/>


### Route checks

Flow validation reads every chain field (`source.before`, `source.next`, `transformer.before`, `transformer.next`, `collector.next`, `destination.before`, `destination.next`) with the same route grammar the runtime uses:

| Check | Level | Example message |
|-------|-------|-----------------|
| A route names a transformer that does not exist | Error `UNKNOWN_ROUTE_TARGET` | `Unknown transformer "x" in route at collector.next` |
| Entries after an unconditional `stop` in a sequence or `one` | Warning | `dead code after stop at ...: entries after an unconditional stop never run` |
| An array made only of route configs (an implicit `one`, the first match wins) | Warning | `first-match array at ...` |
| `many` with no entry, or with a single entry | Warning | `empty many at ...`, `single-entry many at ...` |

At runtime an unknown id is logged and skipped, and the chain continues. A `stop` inside `many` ends only its own copy, so it never makes its siblings dead code. Repeated steps and a transformer's own `next` inside an array are valid and not reported.

### Reference checks

`$flow.`, `$store.`, `$secret.` and `$contract.` resolve only as the whole string value; `$var.` and `$env.` also resolve inline. Flow validation warns when a whole-value reference would not resolve:

| Value | Warning |
|-------|---------|
| `"$flow.server.url/collect"` | `does not match the $flow.NAME grammar (...); it would not resolve. To build a longer string, compose with $var or $env.` |
| `"$secret.api_key"` | `does not match the $secret.NAME grammar (uppercase letters, digits and _); it would not resolve. ...` |
| `"https://x/$store.cache"` | `uses $store. inline. $store. references resolve only as the whole value; it would ship as literal text. ...` |

Values under `title`, `description` and `$comment`, and `$code:` values, are not checked.

### Example checks

Flow validation compares each step's example `out` with the `in` of the steps it connects to. An `out` written as effects (`[["elb", event]]`, `[["return", { "event": ... }]]`, `[["return", [...]]]`) contributes the events those effects pass on; other effects (`message.ack`, `response`, vendor calls, `["return", false]`) pass nothing on.

Contracts are checked where the runtime applies them: only in `@walkeros/transformer-validate` steps. Each validate step's own examples run through that step's `contract`, `mode`, `format` and `output` settings, and the example `out` must agree with the verdict. See [Validate](/docs/getting-started/flow/validate#design-time-checks).

### Options

<CodeSnippet
  code={`walkeros validate [input] [options]`}
  language="bash"
/>

| Option | Description |
|--------|-------------|
| `-t, --type <type>` | Validation type (default: `flow`). Also: `event`, `mapping`, `contract` |
| `--path <path>` | Validate a specific entry against its package schema (e.g., `destinations.snowplow`) |
| `-f, --flow <name>` | Flow name to validate (for multi-flow configs) |
| `-o, --output <path>` | Write result to file |
| `--strict` | Treat warnings as errors (exit code 2) |
| `--json` | Output results as JSON |
| `-v, --verbose` | Show detailed validation information |

### Event validation details

2. **Name is non-empty** - Cannot be empty string

### Mapping validation details

Mapping validation checks (see [mapping.ts](https://github.com/elbwalker/walkerOS/blob/main/packages/cli/src/commands/validate/validators/mapping.ts)):

1. **Object structure** - Must be an object with event patterns as keys
2. **Event patterns** - Must be `"entity action"` format or contain wildcard (`*`)
3. **Rule structure** - Each rule must be an object or array of objects
4. **Catch-all position** - Warns if `*` is not the last pattern

### Contract validation details

Contract validation checks (see [contract.ts](https://github.com/elbwalker/walkerOS/blob/main/packages/cli/src/commands/validate/validators/contract.ts)):

1. **Root structure** - Must be an object of named contract entries, not an array or primitive
2. **Named-entry shape enforced** - A flat entity-action map, or a `$`-prefixed root key, is rejected as the flat shape
3. **Unknown keys** - A key on a contract entry outside `extend`, `tagging`, `description`, `events`, `schema` is a warning, not an error
4. **`tagging`** - If present, must be a number
5. **`schema`** - If present, must be a JSON Schema object
6. **`extend`** - Must reference an existing contract entry; circular chains are rejected
7. **Entity and action keys** - Cannot be empty strings
8. **Event entries** - Each `events.<entity>.<action>` value must be a JSON Schema object

<CodeSnippet

walkeros validate '{
  "web": {
    "tagging": 1,
    "events": {
      "page": {
        "view": {
          "properties": {
            "title": { "type": "string" }
          }
        }
      }
    }
  }
}' --type contract`}
  language="bash"
/>

## Auth commands

The `auth` command group manages authentication with the walkerOS cloud service. Authentication is required for cloud commands (`projects`, `flows`, `deploy`).

### Login

Log in to walkerOS through the RFC 8628 device authorization grant. The CLI asks the app for a one-time code, opens your browser on the approval page, and polls until you approve. No password reaches the CLI and no local callback server is opened, so this works the same over SSH, inside Docker and in a cloud IDE.

<CodeSnippet
  code={`walkeros auth login`}
  language="bash"
/>

Output:
```
! Your one-time code: ABCD-1234
  Authorize here: https://app.walkeros.io/oauth/device?user_code=ABCD-1234

  Opening browser...
  Waiting for authorization... (press Ctrl+C to cancel)

✓ Logged in as user@example.com
  Session stored in ~/.config/walkeros/config.json
```

The session is stored in `~/.config/walkeros/config.json` with `0600` permissions: a short-lived access token, its expiry, and a refresh token the CLI rotates on its own, so a login lasts until you log out. Several walkerOS processes can share one config file, so a refresh runs under a lock beside it (`config.json.lock`) and exactly one of them spends the single-use refresh token.

The connection appears in the app under Account, Connected apps, where disconnecting it stops the CLI on its next call.

For a machine with nobody to approve anything, set `WALKEROS_TOKEN` to an automation token instead (Account, then Automation tokens). It is used as-is and never refreshed.

### Token resolution

The CLI resolves a credential in this order, first match wins:

1. `WALKEROS_TOKEN` environment variable. Used as-is, never refreshed.
2. A static `token` in the config file, written by an older CLI. Honored until it expires, with a one-line notice pointing at `walkeros auth login`.
3. The OAuth session in the config file, written by `auth login`. Refreshed automatically when the access token is close to expiry.
4. Nothing, and cloud commands report "Not authenticated. Run `walkeros auth login` first."

A refresh that cannot reach the app is reported as such and leaves the saved session in place, so the next command tries again rather than sending you back to the browser.

## Previews command

The `previews` command group manages preview bundles: short-lived flow bundles
used to test configuration changes on a real production site before deploying.
Creating a preview mints an app-signed, origin-bound activation grant; opening
`?elbPreview={grant}` on your site verifies the grant locally, with no network
round trip, and swaps in the preview bundle for that browser for the life of
the preview session. Activation links minted for an Observe session
additionally carry an `elbPreviewSession` companion grant, which the previewed
page uses to forward server-bound events to that session's isolated container.

All commands require authentication and a project (set via `WALKEROS_PROJECT_ID`
or `--project`).

### How activation works

A managed web bundle that supports preview activation is produced by the wrap
step's `preview` option, which bakes in a public key keyring, the issuing
environment, and an opaque per-project binding (never a project ID or secret).
The emitted bundle imports `browserSwapActivator` from `@walkeros/core` to
verify an activation grant and swap in the preview artifact. `preview` is the
current wrap option for this; it replaces the earlier `previewOrigin` /
`previewScope` options. A companion `previewGrantTargets` option exists for the
preview artifact itself: it forwards the stored grant as an
`X-Walkeros-Preview` header to named server-bound destinations, so a server
flow can be previewed too. `preview` and `previewGrantTargets` are mutually
exclusive on a single wrap invocation: a host bundle activates a preview, a
preview artifact injects its grant, not both.

## Observe command

The `observe` command group opens an Observe session: a time-boxed window on one
flow that runtimes attach to as arms. A preview arm streams from a browser, a
container arm runs server-side, and both feed one shared journeys feed. See
[Observe](/docs/getting-started/observe) for how a flow connects to an observer
in the first place.

Requires authentication and a project (set via `WALKEROS_PROJECT_ID` or
`--project`).

### observe start

Mint an Observe session for a flow and print the attach info for each arm.

<CodeSnippet
  code={`walkeros observe start <flowId> [options]`}
  language="bash"
/>

| Option | Description |
|--------|-------------|
| `-f, --flow <name>` | Flow settings name, which also picks the arms (auto-resolved when the flow has exactly one) |
| `--project <id>` | Project ID (overrides default) |
| `--level <level>` | Observation detail level: `off`, `standard`, or `trace` |
| `--replace` | Replace an existing active session for this flow |
| `--no-wait` | Do not wait for the session to settle |
| `--timeout <seconds>` | Seconds to wait for the session to settle (default: 300) |
| `--json` | Output the session as JSON |

`--level` steers the provisioned container arm; the web arm's observation detail
does not follow it.

The observed settings picks the arms: a web settings attaches the preview arm,
plus the container arm of any server flow it references; a server settings
attaches the container arm alone.

A settled session renders both arms. An arm this session did not attach renders
as `Web: no web part` or `Server: no server part` in place of its block, so the
output below is the both-arms case:

<CodeSnippet
  code={`Observe session ses_abc123 (live)

    Bundle URL: https://cdn.test/preview/proj_test/walker.k9x2m4p7abcd.js
    Credential: obsw_pb_x.ses_abc123.sec_1
    Activate:   https://shop.example/?elbPreview=header.payload.signature&elbObserve=obsw_pb_x.ses_abc123.sec_1

      WALKEROS_OBSERVER_URL=https://observer.test

      WALKEROS_INGEST_TOKEN=srv_ingest_tok

  Records:  42

  Sessions idle out server-side when no tab or traffic keeps them alive.`}
  language="text"

Open the `Activate:` URL on your site to attach the web arm: the link carries
the session credential, so the page starts posting records without any further

<CodeSnippet
  code={`ENDPOINT=$(walkeros observe start flow_abc123 --flow web)`}

| Code | Meaning |
|------|---------|
| `0` | Session settled (or `--no-wait` returned the mint immediately) |
| `1` | Session failed to arm, or `--timeout` elapsed while it was still arming |

A timeout is not a teardown: the session keeps arming server-side, and it is the
app or a re-run of `observe start` that reports where it landed.

## Running a built flow

The CLI builds flows; it does not start them. A built server flow runs with
`runneros`, the runtime in the separate `@walkeros/runner` package and the
`walkeros/flow` image:

<CodeSnippet
  code={`walkeros bundle flow.json -o dist/
npx --package=@walkeros/runner runneros start dist/flow.mjs`}
  language="bash"
/>

`runneros start` accepts the `flow.mjs` entry of a built directory, a
`.tar.gz`/`.tgz` archive from `walkeros bundle -o flow.tar.gz`, or an http(s)
URL to either. It has no bundler: a local flow config is refused, and one fetched by URL fails to import. See the
[runtime](/docs/apps/runtime) for its options, environment variables, health
checks and the Docker image.

## Cache command

The `cache` command manages the CLI's package and build caches.

### Use Case

The CLI caches downloaded npm packages and compiled builds to speed up repeated operations. You may need to:
- Clear stale cached packages when debugging version issues
- Free up disk space by removing old cached builds
- View cache statistics to understand cache usage

### How Caching Works

The caches live under `cache/` in the system temp directory (`os.tmpdir()`, which reads `TMPDIR` on macOS and Linux). CLI output prints that directory as `$TMPDIR`; on Linux `TMPDIR` is often unset in a shell, so read a printed `$TMPDIR/...` path as the system temp dir (usually `/tmp`).

**Package Cache** (`$TMPDIR/cache/packages/`):
- Mutable versions (`latest`, `^`, `~`) are re-checked daily
- Exact versions (`0.4.1`) are cached indefinitely
- Saves network time on repeated builds
- An entry is written to a temporary sibling and renamed into place once it is complete, so an interrupted write never leaves a partial package behind. A failed write logs a warning and the build continues without caching that package:

```
Package cache write failed for <name>@<version>: <message>. The build continues without caching it.
```

- Entries written by an earlier CLI version carry no completion marker and count as incomplete, so each cached package is downloaded once more after the upgrade.

**Build Cache** (`$TMPDIR/cache/builds/`):
- Caches compiled bundles based on flow.json content + date
- Identical configs reuse cached builds within the same day
- Dramatically speeds up repeated builds (~100x faster)
- Keys cover the config and the resolved package versions, not the files of a local package (`path`). After rebuilding a local package without changing its version, run `walkeros cache clear` to see the change

**Temporary files.** Each run works in its own directory, `$TMPDIR/walkeros/<kind>/<6 characters>` (`kind` is `push`, `build`, `bundle`, `wrap`, `archive` or `setup`), for example `Output: $TMPDIR/walkeros/push/d6WHM6/flow.mjs (1266.1 KB, 0.6s)`, and removes it afterwards. The short names keep these paths readable in masked logs.

### Basic Usage

<CodeSnippet
  code={`# View cache statistics

# Clear all caches
walkeros cache clear`}
  language="bash"
/>

### Commands

**View cache info:**

<CodeSnippet

  language="bash"
/>

```

```

Leftovers of interrupted cache writes are not counted.

**Clear all caches:**

<CodeSnippet
  code={`walkeros cache clear`}
  language="bash"
/>

Clearing also removes the leftovers of interrupted cache writes.

**Clear only package cache:**

<CodeSnippet

/>

## API version compatibility

Official clients (CLI, MCP) send three headers on every request
to the walkerOS app so the server can tell them apart and enforce minimum
versions per endpoint:

- `User-Agent`: e.g. `walkeros-cli/1.4.0 (node/18.19.0; linux)`
- `X-WalkerOS-Client`: `cli` or `mcp`
- `X-WalkerOS-Client-Version`: the installed package version

If you call an endpoint that has been updated in a way that requires a newer
client, the app responds with `426 Upgrade Required`. The CLI prints the
required minimum version and the upgrade command, then exits with code 2:

```
Error: This walkerOS app endpoint requires @walkeros/cli >= 1.5.0
(you have 1.4.0). Upgrade with: npm install -g @walkeros/cli@latest
See https://walkeros.io/docs/upgrading for details.
```

The MCP server surfaces the same information in tool error responses so AI
assistants can tell the user to upgrade. See
[Upgrading](/docs/upgrading) for the full version-negotiation rules.

### Docker Build

The canonical multi-stage Dockerfile installs the CLI in the build stage, bundles the flow into a `dist/` directory, then copies the directory into the runtime image. You do not need to declare step packages in `package.json`; pacote installs them transparently from `flow.json`. The runtime stage has no npm and no bundler.

<CodeSnippet
  code={`ARG WALKEROS_VERSION

FROM node:24-alpine AS builder
ARG WALKEROS_VERSION
WORKDIR /build
RUN npm init -y && npm install --save-dev @walkeros/cli@\${WALKEROS_VERSION}
COPY flow.json ./
RUN npx walkeros bundle flow.json -o dist/

FROM walkeros/flow:\${WALKEROS_VERSION}
COPY --from=builder /build/dist/ /app/flow/`}
  language="dockerfile"
/>

Build it with `docker build --build-arg WALKEROS_VERSION=<version> .`, using a version whose `walkeros/flow` image ships `runneros`. The image supplies `BUNDLE=/app/flow/flow.mjs`, `PORT=8080` and the `runneros start` command. See the [runtime](/docs/apps/runtime#canonical-dockerfile).

## Troubleshooting

### Package Download Issues

If packages fail to download:

<CodeSnippet
  code={`# Clear cache and retry
walkeros bundle flow.json --no-cache

# Check npm registry access
npm ping`}
  language="bash"
/>

### Build Issues

If you encounter build issues:

<CodeSnippet
  code={`# Clear cache and retry
walkeros cache clear

# Retry with verbose output
walkeros bundle flow.json --verbose`}
  language="bash"
/>

### Port Already in Use

If the port is already in use:

<CodeSnippet
  code={`# Start the built flow on a different port
runneros start dist/flow.mjs --port 8081

# Or kill the process using the port
lsof -ti:8080 | xargs kill`}
  language="bash"
/>

### Authentication Issues

If cloud commands fail with authentication errors:

<CodeSnippet
  code={`# Check current identity
walkeros auth whoami

# Re-authenticate
walkeros auth login

# Or use an automation token from Account, Automation tokens
export WALKEROS_TOKEN=wos_pat_xxx`}
  language="bash"
/>

### nft cannot trace a runtime asset

If a runtime asset is missing in `dist/node_modules/` (typically because the dep loads it via a dynamically constructed path), declare it explicitly under the flow's `config.bundle.traceInclude`. Paths and globs both work, resolved against the install root:

<CodeSnippet
  code={`"flows": {
  "default": {
    "config": {
      "platform": "server",
      "bundle": {
        "packages": { "@walkeros/server-destination-gcp": {} },
        "traceInclude": [
          "node_modules/some-pkg/data/*.json"
        ]
      }
    }
  }
}`}
  language="json"
/>

### Caching pacote downloads in CI

The bundler caches downloads under `process.env.NPM_CACHE_DIR` (default
`$TMPDIR/cache/npm`). On CI, persist that path with `actions/cache`:

<CodeSnippet
  code={`- uses: actions/cache@v4
  with:
    path: .walkeros-cache/npm
    key: walkeros-\${{ hashFiles('**/flow.json') }}
- run: npx walkeros bundle flow.json -o dist/
  env:
    NPM_CACHE_DIR: \${{ github.workspace }}/.walkeros-cache/npm`}
  language="yaml"
/>

### Bundle output is large

`dist/node_modules/` for a server flow with the GCP destination typically holds 30-50MB across 10k+ files (grpc, protobufjs, etc.). Recommendations:
- Use `.dockerignore` to exclude irrelevant build output from non-bundle contexts.
- Prefer `COPY --from=builder /build/dist/ /app/flow/` over file-by-file in your Dockerfile.
- Expect ~30s artifact upload time on slow CI.
