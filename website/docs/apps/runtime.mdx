# walkerOS runtime

`runneros` runs a prebuilt walkerOS flow artifact. It ships in the npm package
`@walkeros/runner` and is the entrypoint of the `walkeros/flow` Docker image.
It never builds a flow: you build with [`walkeros bundle`](/docs/apps/cli),
then start the result.

<CodeSnippet
  code={`walkeros bundle flow.json -o dist/
runneros start dist/flow.mjs`}
  language="bash"
/>

The runtime is a separate tool from the CLI, with its own name and
capabilities. It cannot bundle, because it has no esbuild, no package manager
and no registry access.
Hand it a local flow config and it refuses with
`BUNDLE must be a prebuilt artifact (.mjs, .js, .cjs, .tar.gz, .tgz), got flow.json`.

## Build, run, orchestrate

Getting a flow into production has three stages, and each one is kept to what
it needs:

| Stage | Has | Must not have |
|---|---|---|
| **Build** (`walkeros bundle`) | Registry access, esbuild, `@vercel/nft`, a Node toolchain | Production secrets or production traffic |
| **Run** (`runneros start`) | The artifact, its runtime secrets, the port | A package manager, registry egress, a bundler |
| **Orchestrate** (you, your CI, or the walkerOS app) | The decision of what runs where | The ability to execute the artifact |

Build values that a web flow bakes into its public bundle are declared in the
config under `config.bundle.env` and resolved at build time, see
[build-time values](/docs/apps/cli#build-time-values-configbundleenv). Runtime
secrets for a server flow reach the running process through its environment.

## The artifact

`walkeros bundle` produces two shapes, depending on the flow's platform:

| Platform | Artifact | Runs where |
|---|---|---|
| `server` | A **directory**: `dist/flow.mjs`, `dist/package.json` and `dist/node_modules/` (only the files `@vercel/nft` traced) | `runneros start` |
| `web` | A **single file**: `dist/walker.js` | The browser, served by any static host |

A server flow always travels as the whole directory. Copying `flow.mjs` alone
drops `node_modules/`, and a flow with external step packages then fails to
resolve its imports. To ship the directory as one file, bundle to an archive
with `walkeros bundle flow.json -o flow.tar.gz`.

## Quick start

Build, then run the directory in the image:

<CodeSnippet
  code={`npx @walkeros/cli bundle flow.json -o dist/

docker run --rm -p 8080:8080 \\
  -v "$PWD/dist:/app/flow:ro" \\
  walkeros/flow:<version>`}
  language="bash"
/>

Or without Docker:

<CodeSnippet
  code={`npx --package=@walkeros/runner runneros start dist/flow.mjs`}
  language="bash"
/>

Check it is up:

<CodeSnippet code={`curl http://localhost:8080/ready`} language="bash" />

## Image tags

Every `walkeros/flow` tag is the npm version of the `@walkeros/runner` it
contains: `walkeros/flow:<version>` runs `@walkeros/runner@<version>`. Version
tags are immutable. `latest`, `<major>` and `<major>.<minor>` move only on
stable releases.

Tags before `4.7.0` run an older entrypoint without `runneros`. Pin a version
that ships `runneros`, ideally the same version as the
`@walkeros/cli` that built the artifact, and check it with:

<CodeSnippet
  code={`docker run --rm walkeros/flow:<version> runneros --version`}
  language="bash"
/>

The image is published for `linux/amd64` only. On an arm64 host, Docker runs
it under emulation (`--platform linux/amd64`).

## Canonical Dockerfile

Build and run in two stages. The build stage has npm and the registry; the
runtime stage has neither:

<CodeSnippet
  code={`ARG WALKEROS_VERSION

FROM node:24-alpine AS builder
ARG WALKEROS_VERSION
WORKDIR /build
RUN npm init -y && npm install --save-dev @walkeros/cli@\${WALKEROS_VERSION}
COPY flow.json ./
RUN npx walkeros bundle flow.json -o dist/

FROM walkeros/flow:\${WALKEROS_VERSION}
COPY --from=builder /build/dist/ /app/flow/`}
  language="dockerfile"
/>

<CodeSnippet
  code={`docker build --build-arg WALKEROS_VERSION=<version> -t my-flow .
docker run --rm -p 8080:8080 my-flow`}
  language="bash"
/>

- `COPY --from=builder /build/dist/ /app/flow/` copies the whole directory, so
  the traced `node_modules/` comes along.
- The image already sets `BUNDLE=/app/flow/flow.mjs`, `PORT=8080` and
  `CMD ["runneros", "start"]`, so the Dockerfile needs no command and no
  `BUNDLE`.
- One `WALKEROS_VERSION` pins both the CLI that builds and the runtime that
  runs.

## What `runneros start` accepts

`runneros start [artifact]` takes the artifact as an argument, or from `BUNDLE`
when there is none, or `flow.mjs` in the working directory when there is
neither.

| Input | Example | Notes |
|---|---|---|
| Local file | `/app/flow/flow.mjs` (the image default) | `.mjs`, `.js` or `.cjs`. Imported in place, nothing is written |
| Local archive | `/app/flow.tar.gz` | `.tar.gz` or `.tgz` holding `flow.mjs` at its root |
| URL | `https://cdn.example.com/flow.tar.gz` | A presigned URL works. Gzip content is extracted as an archive, anything else is written as `flow.mjs`, so point a server flow at its archive |
| Stdin | `cat flow.mjs \| docker run -i ... walkeros/flow:<version>` | Read only when the given path does not exist. An empty stdin is ignored. Stdin carries one file and no `node_modules/`, so a server flow built by `walkeros bundle` fails to start with `Cannot find package '@walkeros/collector'` |

A fetched, extracted or piped artifact is written to `/app/flow/` when that
directory exists (in the image it does). Outside a container it goes to a
private folder under the system temp directory, one per runtime process, and
nothing is written to the temp directory itself. The folder is removed at a
clean exit and left behind by a killed process. The archive carries every
package its flow imports. A package it lacks is resolved from the folder's
parent folders (Node's module resolution), up to the temp directory's
`node_modules/`, so on a shared host build complete archives. A local path
with any other extension, a `.json` flow config above all, is refused before
anything loads. Content from a URL or stdin is checked only by what it is
written as: a flow config delivered that way is written as `flow.mjs` and then
fails to import with a syntax error. Either way nothing is bundled.

At start the runtime prints `Instance <id>`, a random 16-character hex id that
the heartbeat carries too. Recent errors are persisted to `errors-<port>.jsonl`
in the cache folder. That folder is the instance's own: do not share it between
instances, for example on one volume, since instances that listen on the same
port would write the same file.

### Options

| Flag | Environment fallback | Description |
|---|---|---|
| `[artifact]` | `BUNDLE` | Artifact path or URL |
| `-p, --port <number>` | `PORT` | Port to listen on (default `8080`) |
| `--env-file <path>` | none | Load a dotenv file first. Existing variables win; a group- or other-readable file is refused |
| `--json` | none | JSON output |
| `-v, --verbose` | none | Verbose output |
| `-s, --silent` | none | Suppress output |

## Environment variables

| Variable | Default | Description |
|---|---|---|
| `BUNDLE` | `/app/flow/flow.mjs` in the image | Artifact path or URL |
| `PORT` | `8080` | Port for the health server and the flow's HTTP handler. A source's own `port` setting has no effect under the runtime, and nothing logs that |
| `WALKEROS_CREDENTIAL` | none | The runner's credential (`wos_cred_...`), shown once when you pair a runner in the app. It names the app and the deployment, so no other variable is needed. Read once at start and removed from the environment. Unset, the runtime calls no app |
| `WALKEROS_FLOW_RELEASE` | none | Release the loaded flow must carry, or the runtime refuses to start. The walkerOS app sets it when it deploys a flow |
| `WALKEROS_FLOW_NAME` | none | Flow name the loaded flow must carry, checked only together with `WALKEROS_FLOW_RELEASE`. The walkerOS app sets it |
| `WALKEROS_HEARTBEAT_INTERVAL` | `60` | Seconds between heartbeats. Values below `10`, or not a number, are clamped to `10` |
| `WALKEROS_CACHE_DIR` | `$XDG_CACHE_HOME/walkeros`, else `~/.cache/walkeros` | Where the runtime persists recent errors between restarts. `CACHE_DIR` is read as a fallback |
| `NODE_OPTIONS` | `--max-old-space-size=384 --no-warnings` in the image | Heap cap sized for a 512 MB container. Raise it with the container's memory, and keep `--no-warnings`: the runtime logs Node's process warnings itself |

Every start logs the loaded flow as `Flow: <name> release <release>`. With
`WALKEROS_FLOW_RELEASE` set, a runtime that loaded any other artifact, or one
without a release, never reports ready: it exits with
`Artifact mismatch: expected <name>@<release>, loaded <name>@<release>`.

The credential comes from the environment only, or from the `--env-file` you
name. The runtime reads no config file and no CLI login.

## Connecting to the walkerOS app

A flow runs on its own with no account. One variable connects it to the app:
the runner's credential. On the flow part's Self-hosted tab in the app, click
**Pair a runner** and confirm with your passkey or a code. The auth host then
shows the start config once, with the credential in it. Run it as shown, or
set `WALKEROS_CREDENTIAL` in your shell and pass it on:

<CodeSnippet
  code={`docker run --rm -p 8080:8080 \\
  -v "$PWD/dist:/app/flow:ro" \\
  -e WALKEROS_CREDENTIAL \\
  walkeros/flow:<version>`}
  language="bash"
/>

Keep the credential in your platform's secret store and hand it to the
container as `WALKEROS_CREDENTIAL`, never in the image or a committed file. In
Docker Compose, from a `.env` file next to the compose file:

<CodeSnippet
  code={`services:
  flow:
    image: walkeros/flow:<version>
    ports: ['8080:8080']
    volumes: ['./dist:/app/flow:ro']
    environment:
      WALKEROS_CREDENTIAL: \${WALKEROS_CREDENTIAL}`}
  language="yaml"
/>

On Cloud Run, from Secret Manager:

<CodeSnippet
  code={`gcloud run deploy walkeros-flow \\
  --image registry.example.com/my-flow:1.0.0 \\
  --set-secrets WALKEROS_CREDENTIAL=walkeros-credential:latest`}
  language="bash"
/>

A credential that is never used lapses after 7 days. Once connected it lasts
until you revoke it on the Self-hosted tab, pair the part again, or the
deployment ends. Pairing again ends the earlier credential when the new runner
first connects, so the old runner keeps checking in until then. The tab shows
when the credential last bought a token and from which address. A managed
deployment gets its credential from the app, with nothing to paste.

When connected, the runtime:

- **Fetches secrets once at boot** from `GET /api/runner/secrets` and sets them
  in the environment after the artifact is imported and before the flow
  starts, so `$env.NAME` references in a server flow resolve to them. It sets
  only the names the artifact reads through `$secret` or `$env`; other names
  are not set, and one INFO line names them. A reserved name (such as `PATH`,
  `NODE_OPTIONS`, `PORT` or any name starting with `WALKEROS_`, `NODE_`,
  `NPM_`, `LD_` or `DYLD_`) stops the boot with `secret-reserved`, and a name
  that is already in the environment stops it with `secret-in-env`. Each
  refusal is named in the error. A fetch that fails for a reason other than
  authentication logs a warning and the flow starts. A name the flow reads
  only from code is not set.
- **Checks in** at `POST /api/runner/check-in` every
  `WALKEROS_HEARTBEAT_INTERVAL` seconds with its instance ID, version, uptime,
  event counters, recent errors and log lines (secrets are redacted before
  they leave the process), and the release it runs. A failed check-in is
  logged and never stops the flow.
- **Fetches an artifact URL on the app's origin** with its credential. The
  redirect to the storage carries no credential, and a URL on any other host
  is fetched without one.
- **Signs its flow's ingest writes** when the credential belongs to a
  deployment. The flow's steps get a signer: the usage report signs each report
  when it names no token, and the ClickHouse destination signs each insert
  when its config sets `settings.signed: true` (see
  [Signed inserts](/docs/destinations/server/clickhouse#signed-inserts-to-walkeros-hosted-ingest)).
  Each request gets a fresh signature over its exact bytes, with the
  credential's key, and works without the auth server. The signer never signs
  a request to the app or its auth server, so no step obtains headers for
  them, and no step ever sees the credential.

The credential itself is never sent. With it the runtime buys a token that
lasts 24 hours and works only together with the credential's key, and renews
it every hour. When the auth server cannot be reached, the runtime signs each
request with the credential's key instead and keeps serving; one ERROR line
says so, and one more when a token is bought again. A credential the app
refuses (replaced by a new pairing, revoked, or its deployment ended) writes
one ERROR line, `The app refused this runner's credential (replaced, revoked
or ended); a self-hosted runner is paired again on its Self-hosted tab`, and
the flow keeps serving. When the auth server refuses a token request, the line
names how far this machine's clock is off from the server's.

The artifact itself never changes while the runtime runs. To ship a new
version, bundle again and redeploy.

Every value the flow reads through `$secret` or `$env` is masked by exact
value (6 characters or longer) as `***`, whatever its source: the app, an
`--env-file` or the container's environment. This covers the runtime's own
lines, the flow's lines, the recent errors and log lines a heartbeat carries,
and the `--json` error output. The runtime cannot tell a credential from
config, so a config value of 6 or more characters set in the environment for an
`$env` name (a region, a host, a table name such as `events`) shows as `***`
too. Defaults and shorter values are not masked. The pattern rules also catch
values with a recognizable shape (known token prefixes, private keys,
credential-named fields, long high-entropy strings).

The runtime prints text lines by default. A flow that sets
`collector.logger.format` to `json` prints one JSON object per line instead,
errors and warnings on stderr, which log collectors such as Cloud Run read as
structured logs (see [Logger](/docs/collector/logger#log-format)). The lines
before the flow loads, up to `Health server listening on port <port>`, print
as text, because the runtime learns the format from the flow. The flow's
`logger.level` applies to the collector's lines, and `--verbose` still forces
`DEBUG`.

Log lines print a path under the system temp directory as `$TMPDIR/...`. On
Linux `TMPDIR` is often unset, so read such a path as the system temp
directory (usually `/tmp`).

### Secret fetch failures

| Response | Behavior |
|---|---|
| **401 or 403** | Fatal: the runtime exits. The app refused the credential: replaced, revoked or ended |
| **404** (no secrets configured) | Warning, the runtime continues |
| **Any other error** | Warning, the runtime continues without secrets |

Timeouts, network errors, 429 and 5xx responses are retried a few times with
bounded, jittered backoff before the behavior above applies, so a brief blip
while the container starts does not fail the boot. The same applies to
fetching an artifact from a URL.

## Health checks

The runtime serves two endpoints on `PORT`, independent of the flow's sources:

| Endpoint | Status | Body |
|---|---|---|
| `GET /health` | Always `200` | `{"status":"ok"}` |
| `GET /ready` | `200` once the flow's collector is constructed | `{"status":"ready"}` |
| `GET /ready` | `503` while starting | `{"status":"not_ready"}` |
| `GET /ready` | `503` after a sustained loop of uncaught errors | `{"status":"degraded","reason":"flow degraded, see the runtime log"}` |

Use `/health` for liveness and `/ready` for readiness. The image's
`HEALTHCHECK` polls `/ready` every 30 seconds after a 30-second start period.
A flow that fails to start logs `Readiness failed: <reason>`, and the runtime
closes the port and exits with code 1, so probes get no answer.

Every other request goes to the flow's HTTP handler (for example the Express
source's routes); before a flow is loaded, those answer `503`. A flow whose
sources have no HTTP handler, such as the fetch, AWS and GCP sources built for
their own platforms, still reports ready, and every request answers `503` with
`{"error":"No flow loaded"}`.

## Serving files

The runtime has no static file mode. A server flow serves files the same way
it handles events: the `include` field copies a folder next to the artifact,
the [fs store](/docs/stores) reads from it, and
[`@walkeros/server-transformer-file`](/docs/transformers/file) answers matching
requests:

<CodeSnippet
  code={`{
  "version": 4,
  "include": ["./public"],
  "flows": {
    "default": {
      "config": { "platform": "server" },
      "stores": {
        "files": {
          "package": "@walkeros/server-store-fs",
          "config": { "settings": { "basePath": "./public" }, "file": true }
        }
      },
      "sources": {
        "http": {
          "package": "@walkeros/server-source-express",
          "config": {
            "settings": { "paths": ["/collect", "/static/*path"] },
            "ingest": {
              "map": {
                "method": { "key": "method" },
                "path": { "key": "path" }
              }
            }
          },
          "next": [
            {
              "match": {
                "key": "ingest.method",
                "operator": "eq",
                "value": "GET"
              },
              "next": "file"
            }
          ]
        }
      },
      "transformers": {
        "file": {
          "package": "@walkeros/server-transformer-file",
          "config": { "settings": { "prefix": "/static" } },
          "env": { "store": "$store.files" }
        }
      }
    }
  }
}`}
  language="json"
/>

The source only fills `ingest.method` and `ingest.path` when `config.ingest`
maps them, so without that block the `match` never passes and the `file`
transformer never runs. `paths` must cover the served files: the express source
registers only `/collect` by default, and `/static/*path` is Express 5 wildcard
syntax. `file: true` makes the fs store return the files byte-exact.

`walkeros bundle` copies `public/` into `dist/public/`, and the canonical
Dockerfile's `COPY` of the whole `dist/` directory carries it into the image.
Never include the output directory itself (`include: ["./dist"]` with output
`dist/` is refused as a circular copy), and never point the fs store at a
directory that holds credentials. `include` applies to server builds only: a
web build copies nothing and logs that it ignored `include`.

## File paths at runtime

Before loading a flow, the runtime changes its working directory to the
artifact's directory. Relative paths in flow settings resolve against the
artifact, not your project root: with the artifact at `/app/flow/flow.mjs`,
`"filePath": "./data.json"` reads `/app/flow/data.json`. Use `include` to put
such files next to the artifact. In the example above, a file the fs store
does not find there gets the express source's default answer, `200` with a
1x1 GIF, and the log shows `invalid event rejected` at ERROR.

## Constraints

- **Filesystem.** An archive, URL or stdin input writes to `/app/flow/`, so
  those inputs need that directory writable. A read-only root filesystem, the
  usual ECS and Kubernetes hardening, works only with a local `.mjs` artifact
  already in place (for example the canonical Dockerfile, or a read-only
  mount); an archive there fails with
  `Archive did not contain flow.mjs after extraction to /app/flow`. A
  connected runtime persists recent errors to its cache directory (default
  `~/.cache/walkeros`), which also needs to be writable; the image's
  `/app/cache` is writable by the runtime user, so on a read-only root
  filesystem set `WALKEROS_CACHE_DIR=/app/cache` and mount a volume there.
  Without a writable cache directory, recent errors are not persisted across
  restarts, and the flow still runs.
- **Architecture.** The image is `linux/amd64` only.
- **Signals.** The image runs under tini and shuts the flow down on SIGTERM. The
  shutdown drains within 8 seconds and exits 1 when events were lost or a
  destination did not close cleanly. Set the platform's grace period to at
  least 10 seconds.
- **In-memory default store.** A `state` operation that names no `store` uses
  the collector's in-memory `__cache` store, which lives inside one process.
  Anything relying on it across events (state, deduplication, a rate limiter
  on the default store) is correct only on a single instance. Managed
  deployments scale up to five instances; point such steps at a store shared
  by every instance.
- **User.** The image runs as `walker` (UID 1001). `node_modules/` in the
  image is read-only for that user; under `/app`, only `/app/flow` and
  `/app/cache` are writable.

## Troubleshooting

**`BUNDLE must be a prebuilt artifact`**: the runtime was given a flow config.
Build it first with `walkeros bundle` and start the output.

**`Flow artifact not found: /app/flow/flow.mjs`**: nothing was copied or
mounted at the artifact path. Copy the whole `dist/` directory to `/app/flow/`.

**`Cannot find package` at startup**: only `flow.mjs` was copied, piped or
fetched. A server artifact is the directory, including `node_modules/`, or
its archive.

**`does not provide an export named 'default'` at startup**: a step's package
has no default export (the AWS and GCP sources, for example). Name the export
in the step's [`import`](/docs/apps/cli#named-export-selection-with-import).

**`WALKEROS_CREDENTIAL is not a walkerOS credential`**: the variable holds
something other than the credential the app showed. Copy it again from the
start config, or pair the runner again.

**Exits with a 401 or 403 on secrets**, or **`The app refused this runner's
credential`**: the credential was replaced by a newer pairing, revoked, or its
deployment ended. Pair the runner again on its Self-hosted tab.
