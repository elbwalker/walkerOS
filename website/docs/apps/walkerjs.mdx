# walker.js

<PackageLink github="apps/walkerjs" npm="@walkeros/walker.js" />

Paste one script tag, tag your HTML with `data-elb`, and every interaction
arrives in your `dataLayer` as a rich event, ready for Google Tag Manager.

<WalkerjsSnippet />

walker.js is a ready-made file: the [browser source](/docs/sources/web/browser/),
[session detection](/docs/sources/web/session) without cookies or storage, and
an output that pushes every event to `window.dataLayer`. It reads no
configuration. Place it below your GTM snippet
([details](/docs/guides/gtm#where-to-place-the-tag)).

## Tag your HTML

<CodeSnippet
  code={`<body data-elbglobals="pagetype:product">
  <div
    data-elb="product"
    data-elb-product="name:Cotton Tee;price:25"
    data-elbaction="load:view"
  >
    <button data-elbaction="click:add">Add to cart</button>
  </div>
</body>`}
  language="html"
/>

The page load sends `product view`, the button sends `product add`, both with
`data: { name: 'Cotton Tee', price: 25 }` and `globals: { pagetype: 'product' }`.
[HTML attributes](/docs/sources/web/browser/tagging/html-attributes) covers the
other triggers (`visible`, `impression`, `submit`, `hover`), context, nested
entities and `data-elbuser`.

## Events without an element

Use `elb()` for events no element describes, such as a confirmed order. Add
this stub before the script tag, so calls made before walker.js has loaded are
queued:

<CodeSnippet
  code={`<script>
  function elb() {
    (window.elbLayer = window.elbLayer || []).push(arguments);
  }
</script>`}
  language="html"
/>

<CodeSnippet
  code={`elb('walker user', { id: 'us3r' });
elb('walker globals', { currency: 'EUR' });
elb('order complete', { id: '0rd3r1d', total: 50 });`}
  language="javascript"
/>

Queued calls are delivered in order and before the `page view`, so a
`walker user` queued first applies to the events after it. User and globals
stay set for the rest of the page load. See
[commands](/docs/sources/web/browser/commands).

## Single-page apps

Route changes are tracked automatically. A `pushState` to a new path or query,
a `replaceState` to a new path, and back or forward each send a `page view`
with the new URL and the previous page's URL as `data.referrer`. Hash-only
changes do not count, and route changes never start a new session. Tagged
elements the new route renders fire after its `page view`; elements that stay
on screen across routes fire once per page load.

If your site or a GTM History Change tag calls `elb('walker run')` on route
changes, remove that call: otherwise every navigation sends two page views and
fires the page's `load` elements again. Router details, remounting and what is not
covered: [browser source, single-page apps](/docs/sources/web/browser/#single-page-apps).

## What lands in the dataLayer

Every walkerOS event is one push: the full event plus `event` (its name, with
the space) and `_clear: true`. The `product view` from the example above, with
the values that change on every push shown as placeholders:

<CodeSnippet code={JSON.stringify(productView, null, 2)} language="json" />

| Key | Holds |
| --- | --- |
| `event` | The event name, such as `product view`, for GTM Custom Event triggers |
| `_clear` | Tells GTM to replace each key of this push instead of merging it with the previous value |
| `name`, `entity`, `action` | The event name and its two parts |
| `data` | The entity's properties, or the object passed to `elb()` |
| `globals` | Page-wide properties from `data-elbglobals` and `walker globals` |
| `context` | `[value, order]` pairs from `data-elbcontext` around the element |
| `nested` | Entities inside the tagged element |
| `user` | Set by `walker user` or `data-elbuser` |
| `consent`, `custom` | Set by `walker consent` and extra `elb()` arguments; not GTM Consent Mode |
| `trigger` | What fired the event: `load`, `click`, `visible` and so on |
| `id`, `timestamp`, `timing` | Event id, time in milliseconds, seconds since the page or route started |
| `source` | Where the event came from, with the page `url` and `referrer` |

`user`, `globals` and `consent` are left out of the push while they are empty,
for example `user` until you set one, so a `user` your site pushed stays intact.
Every other key is in every push, `data`, `context` and `custom` even when
empty, so `_clear` wipes the previous event's values from GTM's data model.

Two events need no tagging:

- `page view` on every page load and route change: `data.id` is the path, plus
  `title`, `domain`, `referrer`, and `search` or `hash` when the URL has one.
- `session start` when a visit lands with a fresh navigation from another site,
  from a campaign link (UTM parameters or a click id), or directly. Reloads,
  back and forward, internal links and route changes start none. Nothing
  carries over between page loads, so it marks an entry, not a session to
  compare with GA4.

On a page load, `session start` comes before the `page view`, and so do the
page's tagged `load` elements and queued `elb()` calls.

## Use it in GTM

Create a Custom Event trigger with an event name such as `product view`, and
read values with Data Layer Variables (version 2) such as `data.price`.
[Use walkerOS events in GTM](/docs/guides/gtm) covers triggers, variables, GA4
event names and ecommerce items.

## Privacy

walker.js sets no cookies, writes no localStorage or sessionStorage, and makes
no requests of its own: events only go to `window.dataLayer` on the page. The
file contains the session source's storage code, which never runs in this
setup. Consent is enforced where data leaves the page, by your GTM tags, for
example with Consent Mode.

## Self-host it

Download <WalkerjsUrl /> and serve it from your own domain: no third-party
request, and you decide when to update. That URL always serves the newest patch
of its release line, so it changes without notice and carries no Subresource
Integrity hash. To pin one release, use <WalkerjsUrl pinned />, which never
changes once published. The npm package `@walkeros/walker.js` ships the same
file as `dist/walker.js`.

## walker.js or your own bundle

Use walker.js (the ready-made file) or a bundle you built, never both on one
page. Both attach the same DOM triggers, so every click would be counted twice.

## Need more?

walker.js is fixed on purpose: no destinations besides the dataLayer, no
mapping, no consent rules, no settings. Your own bundle has all of them and
reads the same `data-elb` attributes, so your tagging carries over:

- Build and host it in the [walkerOS app](https://app.walkeros.io).
- Or write a [flow file](/docs/getting-started/flow/) and build it with the
  [CLI](/docs/apps/cli).

Optionally, Tag Mode in the app lets you propose tags on the live page without
editing HTML.

## Troubleshooting

walker.js writes nothing to the console except errors. If events do not show
up:

- Type `dataLayer` in the browser console: walkerOS pushes carry `_clear: true`
  and an `event` such as `page view`.
- Open GTM Preview: each walkerOS event appears by name in the timeline.
- Check the Network tab that `walker.js` loaded. Ad blockers can block it, one
  more reason to self-host.
- An element needs `data-elbaction` with a trigger to send events; `data-elb`
  alone only names the entity.
