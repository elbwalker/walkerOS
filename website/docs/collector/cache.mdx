# Cache

Cache is a built-in config property available on every step type (source, transformer, destination). It prevents redundant processing by caching results and serving them on subsequent matching requests.

## Configuration

Add `cache` to any step in your flow config:

```json
"sources": {
  "express": {
    "package": "@walkeros/server-source-express",
    "config": {
      "ingest": { "map": { "method": "method", "path": "path" } }
    },
    "cache": {
      "rules": [
        {
          "match": { "key": "ingest.method", "operator": "eq", "value": "GET" },
          "key": ["ingest.method", "ingest.path"],
          "ttl": 300
        }
      ]
    }
  }
}
```

`ingest.method` and `ingest.path` exist because `config.ingest` lifts them from
the request. Without it the rule's `match` and `key` find nothing, and nothing
is cached (see [Key Resolution](#key-resolution)).

### Cache Rule Properties

| Property | Type | Description |
|----------|------|-------------|
| `match` | `MatchExpression` | When to apply this cache rule |
| `key` | `string[]` | Dot-paths to build the cache key from |
| `ttl` | `number` | Time-to-live in seconds |
| `update` | `Record<string, Value>` | Source caches only: changes to the cached response, applied on HIT and MISS |

`match` is optional, omit it for an always-match rule.

### Cache Properties

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `stop` | `boolean` | `false` (`true` for sources) | Stop flow on cache HIT and skip remaining steps, returning the cached value |
| `store` | `string` | Built-in memory | Reference to a store in `flow.stores` |
| `namespace` | `string` | _(none)_ | Optional key prefix. Omit to write keys directly to the store. Same store + same key + same namespace = same cache entry. |
| `rules` | `CacheRule[]` | Required | At least one cache rule |

`walkeros validate` does not reject an unknown key in `cache` or in a rule;
such a key has no effect.

## Behavior by Step Type

### Source Cache (stop by default)

Source cache intercepts requests before the pipeline runs. Sources default to `stop: true`. On cache HIT, the cached respond value is returned immediately and the pipeline is skipped, as in the example above. With `stop: false`, a HIT changes nothing: the pipeline runs as on a MISS, and `update` is not applied.

### Transformer Cache (step-level)

Transformer cache skips the transformer's execution on HIT but continues the chain with the cached event. This helps with expensive computations such as API enrichment. With `stop: true`, the remaining chain stops on HIT and downstream transformers and destinations are skipped.

:::note Halt scopes
Transformer caches with `stop: true` in a source chain (`source.before`, `source.next`) or in the collector chain (`collector.next`) halt the event on HIT: no destination sees it. In a destination's `before` chain, a HIT skips the rest of that chain and the destination receives the cached event. Destination caches with `stop: true` halt only the per-destination delivery; sibling destinations still receive the event. To drop an event by rule rather than by cache, use a route `stop` (see [Dropping an event with `stop`](/docs/getting-started/flow/routing#dropping-an-event-with-stop)).
:::

### Destination Cache (deduplication)

Destination cache skips the push on HIT, preventing duplicate events from reaching the destination. Other destinations still receive the event. With `stop: true`, the `before` transformer chain is also skipped on HIT.

## Key Resolution

Cache keys use dot-path resolution from a structured context:

- `ingest.method`: request method from source ingest
- `ingest.path`: request path from source ingest
- `event.name`: event name
- `event.data.id`: nested event data field
- `event.user.loggedIn`: user properties

Ingest holds only the fields the source's `config.ingest` maps. A source cache
sees only `ingest`: `event.` paths resolve in transformer and destination
caches. The resolved paths are joined with `:`; when every path of the rule
resolves empty, the event is not cached, and nothing reports it.

## Update Rules

In a source cache, use `update` to modify the response on both HIT and MISS:

```json
"cache": {
  "rules": [{
    "key": ["ingest.method", "ingest.path"],
    "ttl": 300,
    "update": {
      "headers.X-Cache": { "key": "cache.status" },
      "headers.Cache-Control": { "value": "public, max-age=300" }
    }
  }]
}
```

`cache.status` resolves to `"HIT"` or `"MISS"`. Static values use `{ "value": "..." }`. Transformer and destination caches do not apply `update`, and `walkeros validate` does not flag it there.

## Custom Store

By default, cache uses a shared in-memory store. Reference a custom store for persistence:

```json
{
  "stores": {
    "files": {
      "package": "@walkeros/server-store-fs",
      "config": { "settings": { "basePath": "./cache" } }
    }
  },
  "sources": {
    "express": {
      "package": "@walkeros/server-source-express",
      "config": {
        "ingest": { "map": { "method": "method", "path": "path" } }
      },
      "cache": {
        "store": "files",
        "rules": [{ "key": ["ingest.method", "ingest.path"], "ttl": 300 }]
      }
    }
  }
}
```

The filesystem store keeps entries on the local disk of one instance. To share cache entries across instances, use `@walkeros/server-store-s3` or `@walkeros/server-store-gcs` instead. Do not use the Sheets store as a cache tier (a `cache.store` target): nothing rejects it, but every cache read and write then costs a Sheets request. A cache can still wrap it.

The filesystem store rejects a key that begins with `/` (a `WARN` line, `Path traversal rejected`, and no entry), so start `key` with a field such as `ingest.method`, or set `namespace`.

A cache write that fails writes no log line and the push still reports `ok: true`, so a dedup cache on a store that refuses writes lets duplicates through.
