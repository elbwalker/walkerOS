# Collector

The collector is the processing engine of walkerOS: it receives events from
sources, enriches them with additional data, applies consent rules and routes
them to destinations.

#### What it does

The collector validates and normalizes incoming events and applies privacy
rules and the user's consent preferences. It adds its globals, user and consent
state to every event, then sends the processed events to the configured
destinations.

#### Role in architecture

In the walkerOS data flow, the collector sits between sources and destinations:

## Collector chain (`next`)

The collector's `next` is a transformer chain that runs once per event, after
the collector completed the event and before it hands the event to the
destinations. Every destination receives what the chain produces, so it is the
place for work all destinations share, such as validation or bot scoring.

  sources={{ default: { highlight: false } }}
  collector={{ highlight: false }}
  collectorTransformers={{ collect: { label: 'Transformer(s)', highlight: true } }}
  destinations={{ ga4: { label: 'GA4', highlight: false }, meta: { label: 'Meta', highlight: false } }}
  markers={[
    { position: 'chain-collect', id: '1', text: 'Runs once per event, before the fan-out' },
  ]}
/>

<CodeSnippet
  code={`import { startFlow } from '@walkeros/collector';
import { transformerBot } from '@walkeros/server-transformer-bot';
import { transformerValidate } from '@walkeros/transformer-validate';

await startFlow({
  transformers: {
    bot: { code: transformerBot },
    validate: { code: transformerValidate },
  },
  next: [
    {
      match: { key: 'event.name', operator: 'eq', value: 'product impression' },
      stop: true,
    },
    'bot',
    'validate',
  ],
  destinations: {
    /* ... */
  },
});`}
  language="typescript"
/>

`next` accepts the same `Route` as every other chain field (see
[Chain resolution](/docs/getting-started/flow/routing#chain-resolution)); in a flow
file it is `collector.next`. Its routes read `{ ingest, event }` with the
completed event. What the chain does reaches every destination:

- A `stop` (or a transformer returning `false`) drops the event for **all**
  destinations. To drop an event for one destination only, put the `stop` in
  that destination's `before`.
- A `many` fork delivers each copy to the destinations on its own, each with
  its own `event.id`.
- Consent-queued events, late destinations, and replayed pre-run events receive
  the chain's output; the chain never runs twice for one event.
- `walker config` can replace `next` for later events.

### What a push answers

`elb` and `collector.push` answer a `PushResult`. For each destination the
event ends in one of three places:

* `done`: the destination delivered the event,
* `queued`: the event is waiting, with a `reason`: `consent` (the destination
  waits for a grant), `batch` (it sits in a batch until the flush) or `held`
  (a state delivery to the destination, such as its consent handler, is running or failed; the destination retries once per window),
* `failed`: the destination did not deliver it, with a `reason` that carries
  a `code`, a `message` and `retryable` (see the table in
  [Logger](./logger#failure-codes)).

An event a destination skips on purpose, because a rule has `ignore: true`
or because consent is denied on a server collector, appears under none of the
three and is counted in `status.destinations.<id>.skipped`.

`ok` is `false` when any destination failed, and also when a step before the
destinations failed: `reason` then names the cause, for example `queue-full`
(the collector has not run yet and its queue is full), `transformer` (a
transformer threw or is not ready) or `mapping` (a rule `condition` threw).
Unmet consent is never a failure, so a consent wait answers `ok: true` with
`queued`.

A source that answers a producer reads this result: see
[Producer acknowledgement](/docs/sources/server#producer-acknowledgement).

### What `failed` counts

`collector.status.failed` is the single counter for any walkerOS-internal
pipeline failure. Each destination also counts its own failures in
`status.destinations.<id>.failed`. Contributing sites:

* a destination's `push` or `pushBatch` threw, or the destination reported an
  error through `context.reportError`,
* a destination could not start or did not become ready: `init` threw or did
  not settle within `config.timeout`, an open circuit breaker, a destination
  held past one retry window, a full queue,
* an exception escaped the inner pipeline of `collector.push` or
  `collector.command` (any uncaught error inside the boundary),
* a transformer threw or is not ready,
* a rule `condition` threw (the event fails with `mapping`),
* source startup failures (`code()` threw, `init()` threw, queued-on
  flush threw),
* transformer init failures.

Rejected client input does not increment `status.failed`. An event
the pipeline declares invalid (a missing or malformed `name`) resolves as
`{ ok: false, invalid: true, error }`, logs one warn without a stack, and
counts on `collector.status.sources.<id>.rejected`. That keeps `failed` a
measure of walkerOS faults rather than of whatever the public internet
posts at a collector endpoint.

User-supplied callback throws in `on` subscriptions (`destination.on`,
`source.on`, consent rules, `ready`, `run`, `session`, generic) log at error
level but do not increment `status.failed`. A mapping `fn`, `validate` or
value-level callback that throws drops only that value; the event still goes
out and the collector logs one ERROR line per cause. A destination whose
`on('consent')` handler fails is reported as `consent-not-applied`.

Every failure is written to the log by the collector, once per cause. See
[Logger](./logger#failure-lines) for the line format, the rate limit and the
codes.

A source whose `init()` throws stays with `config.init === false`
instead of being marked initialized, so `source.config.init` shows that the
source did not start.

Alarm on the ratio of `status.failed` to `status.in`. The structured fields of
each line (`step`, `code`, `status`, `retryable`) are enough to filter
destination vs boundary failures downstream.

**Personal data in logs.** Failure lines carry the step id, the cause code,
the HTTP status, the event name, the mapping key and the error message
(capped at 300 characters), never the event's `data`, `user`, `consent`,
`globals`, `context` or `custom`, an ingest value, a vendor response body or a
setting value. A vendor response body stays on the error object.

### Consent-denied events on a server

A collector holds an event that a destination's `consent` does not allow, and
sends it when consent is granted later (`consentDenied: 'queue'`, the
default). A server has no later grant for an event's own consent, so server
flows built by the CLI default to `consentDenied: 'skip'`: the event is not
queued, the destination counts it in `skipped`, and the collector writes a
DEBUG line. Set the value in the flow's `collector` block to choose the other
mode; an authored value always wins. Unmet consent is never an error or a
warning.

<CodeSnippet
  code={`"collector": {
  "consentDenied": "queue"
}`}
  language="json"
/>

A held event keeps the consent it was admitted with: when its destination's
hold ends it is delivered even if the collector's consent changed meanwhile.

### Flushing batches

`walker flush` sends every pending destination batch at once and leaves the
collector running (see [Commands](./commands#walker-flush)). The browser source
sends it when the page goes away.

### Fatal errors

Throw `FatalError` (exported from `@walkeros/core`) for invariant
violations or operator-initiated aborts that must crash the host process.
Standard `Error` is absorbed by the boundary catch, logged, and counted.
`FatalError` bypasses the boundary catch of `collector.push` and
`collector.command` and propagates, so a supervisor (CLI runner, Express
server, container orchestrator) can terminate cleanly. It propagates when
thrown in a source (its factory or `init`), in a transformer's `init` or in an
`on` handler. Thrown in a destination's `init` or `push`, or in a
transformer's `push`, it is handled like any other error thrown there and does
not propagate. Thrown in a mapping callback of a destination, it does not
propagate either, but it fails that destination's push and the event goes to
its dead-letter queue. An ordinary error there drops only the value, or, in a
rule `condition`, makes that rule not match.

<CodeSnippet
  code={`import { FatalError } from '@walkeros/core';

// in a source's or transformer's init
if (!config.apiKey) {
  throw new FatalError('apiKey missing, refusing to start');
}`}
  language="typescript"
/>

Queue sizes and DLQ sizes can be read directly from destination instances, or
from the status snapshot:

<CodeSnippet
  code={`const dest = collector.destinations['meta'];
const queueSize = dest.queuePush?.length || 0;
const dlqSize = dest.dlq?.length || 0;

// Or from status (point-in-time snapshots refreshed after each push pass):
const metaStatus = collector.status.destinations['meta'];
metaStatus.queuePushSize; // events waiting for consent
metaStatus.dlqSize; // failed pushes retained for triage

// Drop counts live on the process-wide \`status.dropped\` map, keyed by
// stepId (use \`stepId()\` from \`@walkeros/core\`):
import { stepId } from '@walkeros/core';
const metaDrops = collector.status.dropped[stepId('destination', 'meta')];
metaDrops?.queue ?? 0; // monotonic count of evicted consent-queued events
metaDrops?.dlq ?? 0; // monotonic count of evicted DLQ entries`}
  language="typescript"
/>

## Buffer bounds

The collector keeps four internal buffers per process. Each is size-bounded
with a configurable cap, and the `dropped` or `failed` counter moves on
overflow. What happens to the entry and how loud it is depends on the buffer:

* `collector.queue` evicts the oldest entry and logs once per overflow window
  at INFO, because it only feeds destinations added later.
* `collector.preRunQueue` refuses the newest event. That push answers
  `ok: false` with the reason `queue-full`, counts as failed and logs an ERROR
  line.
* `destination.queuePush` evicts the oldest consent-waiting event first and
  counts it in `dropped`; it logs once per overflow window at DEBUG, because
  unmet consent is never an error. When the destination is held and the queue
  holds only held events, the newest event is refused and fails with
  `queue-full`.
* `destination.dlq` evicts the oldest failed entry (it was reported failed
  already, only its replay material is lost) and logs an ERROR line.

| Buffer                  | Purpose                                              | Default cap | Config                              |
| ----------------------- | ---------------------------------------------------- | ----------- | ----------------------------------- |
| `collector.queue`       | Replay buffer for late-registered destinations       | 1000        | `Collector.Config.queueMax`         |
| `collector.preRunQueue` | Events pushed before the collector runs              | 1000        | `Collector.Config.queueMax`         |
| `destination.queuePush` | Per-destination consent-denied buffer                | 1000        | `Destination.Config.queueMax`       |
| `destination.dlq`       | Per-destination dead-letter queue of failed pushes   | 100         | `Destination.Config.dlqMax`         |

Each step has its own knob; no cascade. Set the collector cap on the collector,
and per-destination caps on each destination:

<CodeSnippet
  code={`const { collector } = await startFlow({
  // Collector replay buffer cap
  queueMax: 5_000,
  destinations: {
    bigquery: {
      code: bigqueryDestination,
      config: {
        // Keep more failed rows for triage on this destination
        dlqMax: 1_000,
      },
    },
  },
});`}
  language="typescript"
/>

Operators alarm on the `dropped` counters to detect sustained overflow.
Counters live on `collector.status.dropped`, keyed by stepId (build the
key with `stepId()` from `@walkeros/core`):

<CodeSnippet
  code={`import { stepId } from '@walkeros/core';

// Collector replay buffer drops: traffic bursts outrunning destination
// registration.
const collectorDrops =
  collector.status.dropped[stepId('collector')]?.queue ?? 0;

// Events dropped before the collector ran
const preRunDrops = collector.status.dropped['collector.preRun']?.queue ?? 0;

// Destination drops by buffer:
//  - queue: consent-denied events evicted from the destination's queuePush
//  - dlq:   failed-push entries evicted from the destination's DLQ
const ga4Drops = collector.status.dropped[stepId('destination', 'ga4')];
ga4Drops?.queue ?? 0;
ga4Drops?.dlq ?? 0; // sustained non-zero rate signals destination outage`}
  language="typescript"
/>
