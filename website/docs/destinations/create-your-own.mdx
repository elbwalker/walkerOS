# Create Your Own Destination

This guide provides the essentials for building a custom walkerOS destination.

## The destination interface

A destination is an object that implements the `Destination.Instance` interface
from `@walkeros/core`. The most important property is the `push` function,
which is called for every event.

<CodeSnippet
  code={`interface Instance<T extends TypesGeneric = Types> {
  config: Config<T>;
  push: PushFn<T>;
  type?: string;
  env?: Env<T>;
  init?: InitFn<T>;
  pushBatch?: PushBatchFn<T>;
  on?: On.OnFn;
  setup?: SetupFn<Config<T>, Env<T>>;
  destroy?: DestroyFn<Config<T>, Env<T>>;
}`}
  language="typescript"
/>

`T` bundles the destination's own types:
`Destination.Types<Settings, Mapping, Env>`.

## The `push` function

The `push` function is where you'll implement the logic to send the event to
your desired service. It receives the `event` and a `context` object.

<CodeSnippet
  code={`type PushFn<T extends TypesGeneric = Types> = (
  event: WalkerOS.Event,
  context: Destination.PushContext<T>,
) => WalkerOS.PromiseOrValue<void | unknown>;`}
  language="typescript"
/>

The push context contains:

* **`config`**: Destination configuration with settings
* **`env`**: Environment with window, document, etc.
* **`logger`**: Logger instance
* **`id`**: Unique destination identifier
* **`data`**: Pre-computed data from mapping
* **`rule`**: The matching mapping rule for this event
* **`ingest`**: Optional request metadata from source
* **`collector`**: The collector instance
* **`reportError`**: Reports an error raised outside `push`, such as an SDK
  client's `'error'` event, optionally for one event

## Example: A simple webhook destination

Here is an example of a simple destination that sends events to a webhook URL.

<CodeSnippet
  code={`import { StepError, type Destination } from '@walkeros/core';

// 1. Define your settings and bundle your types
interface WebhookSettings {
  url: string;
}

type Types = Destination.Types<WebhookSettings>;

// 2. Create the destination object
export const destinationWebhook: Destination.Instance<Types> = {
  type: 'webhook',
  config: {},

  async push(event, { config, rule }) {
    const { settings } = config;

    // 3. A missing setting is a failure, never a silent return
    if (!settings?.url)
      throw new StepError('Webhook needs settings.url', { code: 'config' });

    // A rule with silent: true sends nothing; the push still returns normally
    if (!rule?.silent) {
      // 4. Send the event and await it; fetch resolves on an error status
      const response = await fetch(settings.url, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(event),
      });
      if (!response.ok)
        throw new StepError(\`HTTP \${response.status}\`, {
          code: 'transport',
          status: response.status,
        });
    }
  },
};`}
  language="typescript"
/>

## Reporting failures

A destination reports a failure by throwing. A `push` that returns normally
counts as delivered, so it must not return early when it could not send, and it
must await every call it makes: a call that is not awaited can fail after the
push has already been counted.

Throw a `StepError` from `@walkeros/core` with a `code`, and optionally the
HTTP `status` and `retryable`. The collector turns the throw into a failed push
with that reason, counts it in the destination's `failed` counter, adds the
event to the dead-letter queue and writes one ERROR line per cause and minute.

* **`config`** - a required setting is missing or invalid (not retryable)
* **`missing-input`** - the event has nothing this destination can send (not
  retryable)
* **`vendor-not-loaded`**, **`vendor-not-ready`**, **`vendor-timeout`** - the
  vendor script is missing, not ready yet or too slow
* **`transport`** - the request failed; a `429` and a `5xx` status are
  retryable, other `4xx` statuses are not

Any other throw is a `transport` failure. `retryable` tells a server source
whether to ask the producer to resend the message. Keep payload data out of the
error message; put a vendor response on the error's `body`, which is never
logged.

A value that cannot be mapped is not a failure of the event: drop that field,
send the event and report the problem once with `reportCause` from
`@walkeros/core`.

`init` follows the same rule. It throws a `StepError` when the destination
cannot start, such as a missing setting or a blocked vendor script, and it does
not return `false`. A destination with a consent requirement is initialized only
once consent is granted, and an `init` that does not settle within the
destination's `config.timeout` (10 seconds by default) fails the waiting pushes
with the `timeout` code.

### Rule options every destination honours

A destination honours `rule.silent`: a rule with `silent: true` sends no event
of its own and only runs the side effects the rule maps, such as an identify.
Skip the send with a condition rather than an early `return`, as in the example
above. A silent rule whose side effects resolve to nothing sends nothing, counts
as delivered and writes one DEBUG line that names the call and the mapping key,
never the value.

### Vendor scripts

A web destination that loads a vendor script uses `loadVendor` from
`@walkeros/web-core`. It injects the script once per page, into the document the destination's `env` provides (the page's own by default), so simulation and server-side rendering work without a browser page. It throws
`vendor-not-loaded`, `vendor-not-ready` or `vendor-timeout`, so a blocked
script shows as failed pushes instead of lost events.

### Conformance test

`@walkeros/collector/dev` exports `conformance`, a test kit that runs a
destination against a real collector and checks, among others, that a failing
send is reported, that a failure never leaks event data into a log line, that a
`silent` example sends nothing and that a revoked consent reaches the vendor.
Call it from a Jest test with the profile that matches the destination:
`http` for a destination that calls `fetch`, `sdk-env` for a server SDK,
`web-sdk` for a web SDK started in `init`, `vendor-global` for a vendor script
that defines a global, or `socket`. A browser profile (`web-sdk`,
`vendor-global`) also needs the `page` option, imported from
`@walkeros/web-core/dev`; without it the test fails and names that import. A setting that only works in pairs, such as
"one of these two", is stated as `anyOf` in the settings schema.

## The `pushBatch` function (optional)

When the destination's config sets `batch` (see
[Batch scheduling](/docs/mapping/rule#batch-scheduling)), the collector buffers
events and calls `pushBatch` once per flush instead of `push` per event.
`batch.entries` holds one entry per event with its `event`, mapped `data`,
`rule`, `ingest` and `respond`. Without `pushBatch`, every event goes to `push` and the
`batch` setting has no effect.

If `pushBatch` throws or rejects, every entry goes to the destination's
dead-letter queue and counts as failed. To report single rows, resolve
`{ failed: [{ index, error }] }` with indices into `batch.entries`: only those
entries fail. A batched event answers `queued` with the reason `batch`, so a
server source acknowledges it when it is queued. A batch flushes after the
`elb` calls that filled it have resolved, so a failed flush shows in the
destination's `failed` counter, the dead-letter queue and one ERROR line, but
the producer's message is not redelivered. A `walker flush` command flushes
all pending batches at once.
Pending batches are flushed at shutdown: the collector waits up to 5 seconds
per flush and logs one that takes longer as failed.

## Schemas {#schema-validation-optional}

A published destination exports JSON Schemas of its `settings` and `mapping`
from `src/dev.ts`, usually written with Zod and converted with `zodToSchema`
from `@walkeros/core/dev`. `walkeros validate`, the MCP tools and the docs read
them from the package's `walkerOS.json` (see
[Package convention](#package-convention)). The
[Meta Pixel](https://github.com/elbwalker/walkerOS/tree/main/packages/web/destinations/meta)
destination is a complete example.

## The `on` method (Optional)

The optional `on` method lets your destination respond to collector lifecycle
events, for example to handle consent changes or session management. Cleanup
belongs in `destroy`.

The collector calls `on` once the destination is initialized. A destination
without an `init` method is initialized without one, when its first event
clears its consent requirement (or consent is granted), and the `on` deliveries
that waited meanwhile reach it then, in order.

### Available Events

* **`consent`**, **`user`**, **`globals`**, **`custom`**, **`config`** - The
  matching `walker` command changed collector state; `context.data` holds the
  values the command set
* **`run`** - The collector started or received `walker run`
* **`ready`**, **`session`** - A `walker ready` or `walker session` command
  (the session source sends `session`); they carry no data

The handler may be async. For `consent`, `user`, `globals` and `custom`, the
collector waits for the handler to settle, up to `config.timeout` (10 seconds
by default), before it pushes events to the destination. If the handler does
not settle in that time, or rejects, the destination's events stay queued
until a later delivery of the state settles, and are discarded at the next
`walker run`. Lifecycle events are awaited too but hold no events, and they can
reach the handler while it is still busy with a state update. The full rules
are in [State delivery](/docs/collector/commands#state-delivery).

### Example: Consent-Aware Destination

<CodeSnippet
  code={`export const destinationWithConsent: Destination.Instance<Types> = {
  type: 'webhook-consent',
  config: {},

  on(type, context) {
    if (type === 'consent') {
      // context.data holds the consent values the command set
      console.log('Consent updated:', context.data);
    }
  },

  push(event) {
    console.log('Event:', event);
  },
};`}
  language="typescript"
/>

## Setup lifecycle (optional)

Components may implement an optional `setup()` lifecycle to provision external resources (BigQuery datasets, Pub/Sub topics, SQLite tables, webhook registrations) before the runtime ever processes events. Setup is **operator-time**: it runs only when an operator explicitly invokes `walkeros setup <kind>.<name>`. The runtime never auto-invokes it.

This separation isolates one-shot infrastructure provisioning from the high-volume event hot path. Production flows can ship with restricted runtime credentials (write-only) while operators run setup with elevated credentials (create) once per environment.

The same lifecycle applies to sources, destinations, and stores. Transformers are pure functions and have no setup.

### Behavior

- Setup is opt-in via `config.setup` in the flow config. The CLI invocation requires it to be `true` or an object; `false` or omitted means the operator's setup invocation is a narrated skip.
- Idempotency is the package's responsibility. Re-running setup against a fully provisioned environment is a safe no-op.
- `walkeros setup` runs `init` first and gives `setup` the config `init` returns, if any; when `init` throws or returns `false`, the command fails with the reason and setup does not run. `destroy` runs after `setup`.
- Structured JSON output is opt-in via `--json` (e.g. `walkeros setup <kind>.<name> --json`). In normal mode the CLI narrates the action and never splices a JSON envelope into the output, even if `setup()` returns a value. The opt-in setup behavior and idempotency are independent of `--json`.

### Example: a destination with setup

<CodeSnippet
  code={`import type { Destination } from '@walkeros/core';

interface BigQuerySettings {
  projectId: string;
  datasetId: string;
  tableId: string;
}

export const destinationBigquery: Destination.Instance<
  Destination.Types<BigQuerySettings>
> = {
  type: 'bigquery',
  config: {},

  async setup({ config }) {
    const { settings } = config;
    if (!settings) return;
    // Create dataset and table if missing. Idempotent: re-running is a no-op.
    // Return any structured result the operator may want to inspect.
    return {
      datasetCreated: settings.datasetId,
      tableCreated: settings.tableId,
    };
  },

  push(event, { config }) {
    // Hot path: only writes rows, never creates resources.
  },
};`}
  language="typescript"
/>

A flow config opts in via `config.setup`, here for the BigQuery destination of `@walkeros/server-destination-gcp`:

<CodeSnippet
  code={`{
  "destinations": {
    "bigquery": {
      "package": "@walkeros/server-destination-gcp",
      "config": {
        "setup": true,
        "settings": {
          "projectId": "my-proj",
          "datasetId": "events",
          "tableId": "raw"
        }
      }
    }
  }
}`}
  language="json"
/>

Then the operator runs:

<CodeSnippet
  code={`walkeros setup destination.bigquery`}
  language="bash"
/>

## Using your destination

To use your custom destination, add it to the `destinations` object in your
collector configuration.

<CodeSnippet
  code={`import { startFlow } from '@walkeros/collector';
import { destinationWebhook } from './destinationWebhook';

const { elb } = await startFlow({
  destinations: {
    myWebhook: {
      code: destinationWebhook,
      config: {
        settings: {
          url: 'https://api.example.com/events',
        },
      },
    },
  },
});`}
  language="typescript"
/>

## Environment dependencies (testing)

The `env` parameter injects external APIs and SDKs into your destination, so
you can test its logic without making actual API calls or requiring real
browser globals.

Use cases:

* Mock external SDKs (Google Analytics, Facebook Pixel, AWS SDK)
* Test without network requests
* Simulate different API responses
* Run tests in any environment (Node.js, browser, CI)

### Defining an Environment

Define the external dependencies your destination needs:

<CodeSnippet
  code={`// types.ts - Web destination
import type { DestinationWeb } from '@walkeros/web-core';

export interface Env extends DestinationWeb.Env {
  window: {
    gtag: (command: string, ...args: unknown[]) => void;
  };
}

// types.ts - Server destination
import type { DestinationServer } from '@walkeros/server-core';
import type { BigQuery } from '@google-cloud/bigquery';

export interface Env extends DestinationServer.Env {
  BigQuery?: typeof BigQuery;
}`}
  language="typescript"
/>

### Using Environment in Your Destination

Add `Env` as the third type of your `Types` bundle for type safety, then
access env in `init` or `push`:

<CodeSnippet
  code={`import type { Destination } from '@walkeros/core';
import type { DestinationWeb } from '@walkeros/web-core';
import { getEnv } from '@walkeros/web-core';

interface Settings {
  /* ... */
}
interface Mapping {
  /* ... */
}
interface Env extends DestinationWeb.Env {
  window: { customAPI: (event: string) => void };
}

// Env is the third type of the bundle
type Types = Destination.Types<Settings, Mapping, Env>;

export const destination: DestinationWeb.Destination<Types> = {
  type: 'custom',
  config: {},

  async init({ config, env }) {
    // Initialize SDK using env, falls back to real APIs
    const { window } = getEnv<Env>(env);
    window.customAPI('init');
    return config;
  },

  push(event, { config, env }) {
    const { window } = getEnv<Env>(env);
    window.customAPI(event.name);
  },
};`}
  language="typescript"
/>

### Creating Test Environments

Create reusable mock environments in an `examples/env.ts` file:

<CodeSnippet
  code={`// examples/env.ts
import type { Env } from '../types';

const noop = () => {};

export const push: Env = {
  window: {
    customAPI: noop,
  },
};

// Call paths that simulate records
export const simulation = ['call:window.customAPI'];`}
  language="typescript"
/>

Export from your examples index:

<CodeSnippet
  code={`// examples/index.ts
export * as env from './env';`}
  language="typescript"
/>

### Using in Tests

Tests push events through `startFlow` with this env and compare the recorded
calls with your step examples, as in
[Using examples in tests](/docs/getting-started/flow/step-examples#using-examples-in-tests).

Key points:

* **Production**: No `env` needed, uses real APIs (window, fetch, SDKs)
* **Testing**: Provide `env` with mocks for isolated testing
* **Type Safety**: `Env` in your `Types` bundle types `env` in `init` and `push`
* **Fallback**: `getEnv(env)` automatically uses real APIs if env not provided
* **Reusable**: Store mock environments in `examples/env.ts` for consistency
* **Simulate**: `walkeros push --simulate` runs the destination with `examples.env.push` and refuses a destination that has none, so it never calls the real vendor. Next to it, export `simulation`, the call paths that carry the vendor request (for example `['sendServer']` or `['call:PubSub.topic.publishMessage']`), which simulate records and prints
* **Keep injected clients**: when `init` builds an SDK client, reach it through `env` and create one only when none is injected, so the mock env reaches the request call

## Package convention

Every walkerOS package includes machine-readable metadata for tooling and discovery.

### `walkerOS` field in package.json

<CodeSnippet
  code={`{
  "walkerOS": { "type": "destination", "platform": "web" },
  "keywords": ["walkerOS", "walkerOS-destination"]
}`}
  language="json"
/>

| Field | Required | Description |
|-------|----------|-------------|
| `walkerOS` | Yes | Object with `type` and `platform` metadata |

### Build-time generation

Use `buildDev()` from the shared tsup config to auto-generate `walkerOS.json`:

<CodeSnippet
  code={`import { buildDev } from '@walkeros/config/tsup';`}
  language="typescript"
/>

This file contains your package's JSON Schemas and examples, so MCP tools and the CLI can validate configurations without installing your package.

`buildDev()` fails the build when the package publishes no `schemas.settings`. A package with two or more `walkerOS.exports` also exports `exportExamples` and `exportSchemas` from `src/dev.ts`, each listing exactly those exports, the default included, with `settings` in every `exportSchemas` entry; a package with fewer exports sets neither.

### Optional: Hints

Packages can export a `hints` record from `src/dev.ts` with short notes that schemas and examples do not cover, such as authentication methods, storage behavior, or troubleshooting tips. Hints are serialized into `walkerOS.json` and surfaced via MCP tools. See the `walkeros-create-destination` skill for details.

## Publishing checklist

- [ ] `walkerOS` field in package.json
- [ ] Keywords include `walkerOS` and `walkerOS-destination`
- [ ] `buildDev()` in tsup.config.ts
- [ ] `schemas.settings` exported from `src/dev.ts` (per export for multi-export packages)
- [ ] `dist/walkerOS.json` generated on build
- [ ] `npm run test` passes
- [ ] `npm run lint` passes
