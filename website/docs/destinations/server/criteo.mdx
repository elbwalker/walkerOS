# Criteo Events API

<PackageLink env="server" github="packages/server/destinations/criteo" npm="@walkeros/server-destination-criteo" status="beta" />

Server-side event delivery to Criteo's Events API (S2S v0) for retargeting. Sending from the server avoids browser limitations and gives Criteo consistent user matching for ad optimization.

## Failures

A response outside the 2xx range, a network error, or no answer within 5 seconds fails the event: the push answers `failed` with the code `transport` (with the HTTP status) or `timeout`, the event goes to the dead-letter queue, and the collector logs one ERROR line. Any 2xx answer counts as delivered: the destination does not read the response body. Without `partnerId` or `callerId` the destination does not start: every push answers `failed` with the code `config`, and the collector logs `destination init failed`. A rule with `silent: true` sends nothing.

## Client IP and user agent

The destination sends the client IP as `ip` and the user agent as `useragent` by default. The `ip` and `userAgent` settings resolve against `{ ingest, event }` and default to `["ingest.ip", "event.user.ip"]` and `["ingest.userAgent", "event.user.userAgent"]`, so they fill in whenever the source provides them (see the `config.ingest` recipe on the [Express source](/docs/sources/server/express#ingest-metadata)). A value that `user_data` in settings maps to `ip` or `useragent` wins; a rule's `data` is not read for them. A value that resolves to nothing is not sent. Set either setting to `false` to turn it off, or to another mapping value to read it elsewhere.

## Consent

The quickstart sets no `config.consent`, so Criteo receives every event, whatever consent the event carries. To send only events with consent, add `consent: { marketing: true }` to `config`, next to `settings` (with several keys listed, one granted key is enough). An event without that consent is skipped or queued, depending on the collector's `consentDenied`. Server flows built by the CLI skip it and count it in `skipped`. With `startFlow` it waits in the destination's queue by default: a later event that carries consent does not release it, and only a `walker consent` command does, which then sends the waiting events of every user at once. Pass `consentDenied: 'skip'` to `startFlow` to skip such events instead (see [Gate a destination with consent](/docs/guides/consent#gate-a-destination-with-consent) and [consent-denied events on a server](/docs/collector#consent-denied-events-on-a-server)).

## Event mapping

Criteo uses its own standard event names. Set the Criteo event name via each rule's `name` field.

| walkerOS Event     | Criteo Event Name       |
| ------------------ | ----------------------- |
| `page view`        | `viewHome` / `viewPage` |
| `product view`     | `viewItem`              |
| `product list`     | `viewList`              |
| `product add`      | `addToCart`             |
| `cart view`        | `viewBasket`            |
| `checkout start`   | `beginCheckout`         |
| `checkout payment` | `addPaymentInfo`        |
| `order complete`   | `trackTransaction`      |
| `user login`       | `login`                 |

An event without a rule `name` is sent under its walkerOS name, such as `page view`, which is not a Criteo event name.

## User identity

Criteo matches users via three signals. Wire them through `user_data` in settings. Only these three keys are read there (besides `ip` and `useragent`), each as one value:

| Field                 | Description                                           |
| --------------------- | ----------------------------------------------------- |
| `mapped_user_id`      | Criteo GUM ID                                         |
| `email`               | Raw email. Hashed into MD5, SHA-256 and SHA-256(MD5)  |
| `retailer_visitor_id` | Stable retailer visitor identifier                    |

Any other key, a list, and a `user_data` object in a rule's `data` are dropped without a log line.

<CodeSnippet
  code={`"settings": {
  "partnerId": "12345",
  "callerId": "YOUR_CALLER_ID",
  "user_data": {
    "mapped_user_id": "user.id",
    "email": "user.email",
    "retailer_visitor_id": "user.device"
  }
}`}

## Email hashing

Raw emails are lowercased and trimmed, then hashed into all three formats Criteo expects:

- `md5`: MD5 hex digest
- `sha256`: SHA-256 hex digest
- `sha256_md5`: SHA-256 hex of the MD5 hex string

A value that is already a hash is not hashed again: a 64-character hex value is sent as `sha256` only, and a 32-character hex value is sent as `md5`, with `sha256_md5` derived from it.

## Deduplication

Criteo Events API supports deduplication with Criteo OneTag by sharing a `deduplication_page_view_id` across channels. Wire it via `data.map.deduplication_page_view_id` in the event mapping.
