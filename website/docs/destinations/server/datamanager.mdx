# Google Data Manager API

server to Google Ads, Display & Video 360 and Google Analytics 4 through one

## Installation

<Quickstart data={data} />

The destination authenticates with Application Default Credentials: the `GOOGLE_APPLICATION_CREDENTIALS` environment variable, or the metadata server on Google Cloud. To use a service account instead, set `config.credentials` to its `client_email` and `private_key`, or `settings.keyFilename` to the path of its key file. If no credentials are found, the destination does not start: every push answers `failed` with the code `config`, and the collector logs `destination init failed`.

The destination sends an event only when its mapped data carries a `transactionId`; any other event fails with the code `missing-input` and one ERROR line (`transactionId is required`). The quickstart maps none, so add one, for example `data: { map: { transactionId: 'id' } }` in `config` to use the walkerOS event ID. For an order that the Google tag also reports, map the order ID the tag sends instead, like `data.id` in the order's rule: Google deduplicates the two by `transactionId` within one conversion action, so the values must match ([additional data sources](https://support.google.com/google-ads/answer/16542291)). With a Google Analytics destination (`accountType: 'GOOGLE_ANALYTICS_PROPERTY'`), an event without an `eventName` fails the same way.

## Failures

A response outside the 2xx range, a 2xx answer that reports validation errors or cannot be read, a network error, a failed token request, or no answer within the collector's 10-second timeout fails the event with the code `transport` or `timeout`: the event goes to the dead-letter queue and the collector logs one ERROR line without the response body. A rule with `silent: true` sends nothing.

## Guided mapping helpers

Define common fields once in Settings instead of repeating them in every event
mapping. Event mappings always override Settings helpers.

<CodeSnippet
  code={`await startFlow({
  destinations: {
    datamanager: {
      code: destinationDatamanager,
      config: {
        credentials: { /* ... */ },
        settings: {
          destinations: [...],

          // Guided helpers (apply to all events)
          userData: {
            email: 'user.email',
            phone: 'data.phone',
          },
          userId: 'user.id',
          clientId: 'user.device',                  // GA4 web stream
          appInstanceId: 'user.appInstanceId',      // GA4 app stream (Firebase)
          sessionAttributes: 'context.sessionAttributes',

          // Consent mapping
          consentAdUserData: 'marketing',
          consentAdPersonalization: 'personalization',
        },
      },
    },
  },
});`}
  language="typescript"
/>

**Consent mapping**: a string names a key of the event's consent, a boolean is a static value. The collector hands a destination only the consent states an event grants, so a string sends `CONSENT_GRANTED` when the event grants that key and nothing for it when the event denies it: Google never receives `CONSENT_DENIED` from an event's consent. A static `false` sends `CONSENT_DENIED`. The request-level `settings.consent` fills in for every event that carries no consent of its own, so with `settings.consent` set to `CONSENT_GRANTED`, an event whose consent denies the mapped key is sent as granted.

## User data

The destination reads these keys from the mapped data (Settings helpers, then `config.data`, then the rule's `data`):

- `email`, `phone`, `firstName` and `lastName`: normalized and SHA-256 hashed.
- `regionCode` and `postalCode`: sent unhashed, as Google requires.
- `userId`, `clientId`, `appInstanceId`, `gclid`, `gbraid`, `wbraid` and `sessionAttributes`: sent as mapped.
- `transactionId`, `conversionValue`, `currency`, `eventName`, `cartData`, `storeId`, `eventSource`, `adUserData`, `adPersonalization`, `ipAddress` and `userAgent`: the event's conversion, consent and device fields, not hashed.

Any other key, a list, and a `user_data` or `userData` object in a rule's `data` are dropped without a log line. There is no `doNotHash`: a value that is already a hash is hashed again.

Normalization follows Google's [formatting rules](https://developers.google.com/data-manager/api/devguides/concepts/formatting) with these gaps today: for `gmail.com` and `googlemail.com` addresses dots are removed but a `+alias` is kept; spaces inside an email are kept; a family name ending in `v`, `iv`, `ii` or `iii` without a space before it loses those letters (`Ivanov` is hashed as `ivano`); and a phone number without a leading `+` gets `+1` when it has 10 digits or fewer, or only a `+` otherwise. Map phone numbers in E.164 format (`+491701234567`).

## Client IP and user agent

The destination sends the client IP and user agent as `eventDeviceInfo.ipAddress`
and `eventDeviceInfo.userAgent` by default. The `ip` and `userAgent` settings
resolve against `{ ingest, event }` and default to `["ingest.ip", "event.user.ip"]`
and `["ingest.userAgent", "event.user.userAgent"]`, so they fill in whenever the
source provides them (see the `config.ingest` recipe on the
[Express source](/docs/sources/server/express#ingest-metadata)). A value your event mapping sets
for `ipAddress` or `userAgent` wins; a value that resolves to nothing is not
sent. Set either to `false` to turn it off:

<CodeSnippet
  code={`settings: {
  destinations: [...],
  ip: false,                          // never send the client IP
  userAgent: 'ingest.userAgent',      // request only, ignore event.user
}`}
  language="typescript"
/>

## Consent

The quickstart sets no `config.consent`, so Google receives every event with its user data, whatever consent the event carries, and a denial is not passed on (see **Consent mapping** above). To send only events with consent, add `consent: { marketing: true }` to `config`, next to `settings` (with several keys listed, one granted key is enough). An event without that consent is skipped or queued, depending on the collector's `consentDenied`. Server flows built by the CLI skip it and count it in `skipped`. With `startFlow` it waits in the destination's queue by default: a later event that carries consent does not release it, and only a `walker consent` command does, which then sends the waiting events of every user at once. Pass `consentDenied: 'skip'` to `startFlow` to skip such events instead (see [Gate a destination with consent](/docs/guides/consent#gate-a-destination-with-consent) and [consent-denied events on a server](/docs/collector#consent-denied-events-on-a-server)).

## Simulate

`walkeros push --simulate destination.<id>` uses the package's mock env for the
auth client and `fetch`, so no token is requested and nothing reaches Google.
The output shows the `fetch` call with the request body the destination would
send.

## Store sales (IN_STORE)

For physical store conversions, set `eventSource: 'IN_STORE'` on the destination
and map a `storeId` in the event mapping. The destination wraps it into the
API's required `eventLocation.storeId` shape.

<CodeSnippet
  code={`mapping: {
  order: {
    complete: {
      name: 'purchase',
      data: {
        map: {
          transactionId: 'data.id',
          conversionValue: 'data.value',
          currency: 'data.currency',
          storeId: 'data.storeId',
          email: 'user.email', // hashed PII still applies
        },
      },
    },
  },
}`}
  language="typescript"
/>
