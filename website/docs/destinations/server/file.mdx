# File

<PackageLink env="server" github="packages/server/destinations/file" npm="@walkeros/server-destination-file" status="beta" />

Local filesystem sink for walkerOS server flows. Appends events to a file as JSON Lines (JSONL), tab-separated values (TSV), or comma-separated values (CSV). Useful for debug logging, audit trails, replay sources, and lightweight local persistence without standing up a database or external service.

## Installation

The destination opens one long-lived `WriteStream` per resolved filename during `init()` (for static filenames) or on first matching event (for dynamic filenames). On flow hot-swap or server shutdown, `destroy()` closes all cached streams.

## Filename templating

`filename` accepts either a static string or a standard walkerOS `Mapping.Value`. Common patterns:

### Tenant sharding

<CodeSnippet
  code={`{
  "filename": { "key": "data.tenant" }
}`}
  language="json"
/>

Each event lands in a file named after the tenant value (e.g. `acme`, `globex`), without an extension. An event whose mapping resolves to no name fails with a `missing-input` error and is not written.

A mapping value runs one operator, so `fn` next to `key` never runs. For a `.jsonl` extension, build the whole name in `fn`:

<CodeSnippet
  code={`{
  "filename": {
    "fn": "$code:(event) => event.data.tenant && \`\${event.data.tenant}.jsonl\`"
  }
}`}
  language="json"
/>

### Daily rotation

<CodeSnippet
  code={`{
  "filename": {
    "fn": "$code:(event) => \`events-\${new Date(event.timestamp).toISOString().slice(0, 10)}.jsonl\`"
  }
}`}
  language="json"
/>

The function receives the event being processed. Each UTC day gets its own file, created by that day's first event, without `logrotate` or cron.

## Formats

### JSONL (default)

One JSON object per line. The entire event is serialised with `JSON.stringify`. Easy to ingest with `jq`, DuckDB (`read_json_auto`), ClickHouse `JSONEachRow`, BigQuery external tables, and Athena.

### TSV / CSV

Specify `fields: string[]` listing the event paths to extract as columns, in that order. Object values are JSON-stringified into a single cell, a missing value is an empty cell, and no header row is written. CSV output follows RFC 4180 quoting. TSV writes each value as it is, so a tab inside a value shifts the following columns and a line break splits the row: use CSV for free text. `format: "tsv"` or `"csv"` without `fields` fails at init with a `config` error.

<CodeSnippet
  code={`{
  "filename": "events.csv",
  "format": "csv",
  "fields": ["timestamp", "name", "data"]
}`}
  language="json"
/>

## Limits

- One file handle is opened per resolved filename and kept open until `destroy()`. Sharding by high-cardinality keys (e.g. `user.session`) can exhaust the OS file descriptor table. Be deliberate about cardinality.
- External rotation (e.g. `logrotate`) leaves the cached handle pointing at the rotated inode. Use the date-token pattern above instead.
- There is no batching: each event is one write, and its push resolves once the line is written. A `batch` setting has no effect, and the collector logs an ERROR line that names it.
- A file that cannot be opened or written (for example `EACCES`, `ENOSPC` or `EISDIR`) fails the event with a `transport` error that names the code, and the event goes to the dead-letter queue ([when delivery fails](/docs/destinations#when-delivery-fails)). The process keeps running, and the next event opens the file again.
