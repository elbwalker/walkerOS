# HubSpot

<PackageLink env="server" github="packages/server/destinations/hubspot" npm="@walkeros/server-destination-hubspot" status="beta" />

Server-side event delivery to [HubSpot](https://www.hubspot.com/) via the official [`@hubspot/api-client`](https://www.npmjs.com/package/@hubspot/api-client) SDK. Sends custom behavioral events, updates contact properties via the CRM API, and batches events through the collector's `config.batch`.

## Consent

The quickstart sets no `config.consent`, so HubSpot receives every event, whatever consent the event carries. To send only events with consent, add `consent: { marketing: true }` to `config`, next to `settings` (with several keys listed, one granted key is enough). An event without that consent is skipped or queued, depending on the collector's `consentDenied`. Server flows built by the CLI skip it and count it in `skipped`. With `startFlow` it waits in the destination's queue by default: a later event that carries consent does not release it, and only a `walker consent` command does, which then sends the waiting events of every user at once. Pass `consentDenied: 'skip'` to `startFlow` to skip such events instead (see [Gate a destination with consent](/docs/guides/consent#gate-a-destination-with-consent) and [consent-denied events on a server](/docs/collector#consent-denied-events-on-a-server)).

## Identity

Every event must be associated with a contact via `email` or `objectId`. The `email` path defaults to `user.email`. An event where neither value can be resolved fails with the `missing-input` code, and a failed HubSpot call fails the push with HubSpot's HTTP status. A `429` and a `5xx` answer are retryable.

## Batching

Set `config.batch` to send events through HubSpot's batch API instead of one
request per event. The options are in
[Batch scheduling](/docs/mapping/rule#batch-scheduling). A flush sends chunks of
500 events, and each event keeps its own outcome.

<CodeSnippet
  code={`"config": {
  "batch": { "size": 100, "wait": 5000 },
  "settings": {
    "accessToken": "$secret.HUBSPOT_ACCESS_TOKEN",
    "eventNamePrefix": "YOUR_EVENT_NAME_PREFIX"
  }
}`}
  language="json"
/>

A batched event answers `queued` with the reason `batch`. A failed flush is
reported (one ERROR line, the failed counter, the dead-letter queue), but the
producer's message is not redelivered.

## Contact update {#contact-upsert}

Use the `identify` setting (destination-level or per-rule) to update HubSpot contact properties alongside event tracking. The resolved mapping must produce `{ email, properties }`, and the destination updates the contact with that email (not an upsert). When HubSpot refuses the update, the push fails with HubSpot's status and the event itself is not sent. When the mapping resolves without an email, the destination skips the update and logs it at DEBUG only; the event is still sent. State-based dedup prevents redundant API calls when identity has not changed.
