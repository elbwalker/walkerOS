## Failures

A response outside the 2xx range, a network error, or no answer within 5 seconds fails the event: the push answers `failed` with the code `transport` (with the HTTP status) or `timeout`, the event goes to the dead-letter queue, and the collector logs one ERROR line. Any 2xx answer counts as delivered: the destination does not read the response body. Without `accessToken` or `conversionRuleId` the destination does not start: every push answers `failed` with the code `config`, and the collector logs `destination init failed`. A rule with `silent: true` sends nothing.

## Consent

The quickstart sets no `config.consent`, so LinkedIn receives every event, whatever consent the event carries. To send only events with consent, add `consent: { marketing: true }` to `config`, next to `settings` (with several keys listed, one granted key is enough). An event without that consent is skipped or queued, depending on the collector's `consentDenied`. Server flows built by the CLI skip it and count it in `skipped`. With `startFlow` it waits in the destination's queue by default: a later event that carries consent does not release it, and only a `walker consent` command does, which then sends the waiting events of every user at once. Pass `consentDenied: 'skip'` to `startFlow` to skip such events instead (see [Gate a destination with consent](/docs/guides/consent#gate-a-destination-with-consent) and [consent-denied events on a server](/docs/collector#consent-denied-events-on-a-server)).

## User identification

The destination builds a `userIds` array from the event data. At least one identifier is required; an event without one fails with `missing-input`.

**SHA256_EMAIL**: resolved from `event.user.email` or a `user_data.email` mapping. The email is normalized (trimmed, lowercased) and SHA-256 hashed before sending. Set `doNotHash: ['email']` if you are pre-hashing upstream: the email is then sent trimmed and lowercased, but not hashed.

**userInfo**: `firstName` and `lastName` mapped in `user_data` are sent together as `user.userInfo`, with `title`, `companyName` and `countryCode` when mapped; with only one of the two names, none of these fields is sent. LinkedIn takes them in plain text, so they leave your server unhashed.

**LINKEDIN_FIRST_PARTY_ADS_TRACKING_UUID**: the LinkedIn click ID (`li_fat_id`). The [session source](/docs/sources/web/session#session-start-event) reads it from the landing page URL into its `session start` event only, so carry it to your conversion events yourself (the snippet reads `context.li_fat_id`). Map it via `user_data` in settings or through event mapping:

<CodeSnippet
  code={`"settings": {
  "accessToken": "$secret.LINKEDIN_ACCESS_TOKEN",
  "conversionRuleId": "12345678",
  "user_data": {
    "li_fat_id": "context.li_fat_id"
  }
}`}
  language="json"
/>

Every other key in `user_data` (besides `email`, `li_fat_id` and the five `userInfo` keys) is dropped without a log line, and a list mapped to `email` is ignored in favour of `event.user.email`.

## Per-event conversion override

The default `conversionRuleId` from settings applies to all events. Override it per event via mapping to route different events to different Campaign Manager conversion rules:

<CodeSnippet
  code={`"mapping": {
  "order": {
    "complete": {
      "settings": {
        "conversion": {
          "map": {
            "ruleId": { "value": "99887766" },
            "value": "data.value",
            "currency": { "key": "data.currency", "value": "EUR" }
          }
        }
      }
    }
  }
}`}
  language="json"
/>

When `currency` resolves to nothing, the value is sent in `USD`.

## Browser deduplication

When you run both the web [LinkedIn Insight Tag](/docs/destinations/web/linkedin) and this server destination, LinkedIn needs a separate conversion rule for each data source: the Insight Tag rule's ID goes in the web destination's `conversion.id`, the Conversions API rule's ID in `conversionRuleId` here. This destination sends the event's `id` as `eventId`; map `eventId: 'id'` on the web side so both send the same ID. LinkedIn then counts a conversion it receives from both once, under the Insight Tag rule ([deduplication](https://learn.microsoft.com/en-us/linkedin/marketing/conversions/deduplication)).
