## Failures

Pinterest can answer HTTP 200 and report an event as `failed` in the body. That counts as a failed push, not as delivered: the event reaches the dead-letter queue and the collector logs one ERROR line. A response outside the 2xx range, a network error, or no answer within 5 seconds fails the event too: the push answers `failed` with the code `transport` (with the HTTP status) or `timeout`. Without `accessToken` or `adAccountId` the destination does not start: every push answers `failed` with the code `config` and the collector logs `destination init failed`. A rule with `silent: true` sends nothing.

## Client IP and user agent

The destination sends the client IP as `user_data.client_ip_address` and the user agent as `user_data.client_user_agent` by default. The `ip` and `userAgent` settings resolve against `{ ingest, event }` and default to `["ingest.ip", "event.user.ip"]` and `["ingest.userAgent", "event.user.userAgent"]`, so they fill in whenever the source provides them (see the `config.ingest` recipe on the [Express source](/docs/sources/server/express#ingest-metadata)). A value your mapping sets for `user_data.client_ip_address` or `user_data.client_user_agent` wins. A value that resolves to nothing is not sent. Set either setting to `false` to turn it off, or to another mapping value to read it elsewhere.

## Consent

The quickstart sets no `config.consent`, so Pinterest receives every event, whatever consent the event carries. To send only events with consent, add `consent: { marketing: true }` to `config`, next to `settings` (with several keys listed, one granted key is enough). An event without that consent is skipped or queued, depending on the collector's `consentDenied`. Server flows built by the CLI skip it and count it in `skipped`. With `startFlow` it waits in the destination's queue by default: a later event that carries consent does not release it, and only a `walker consent` command does, which then sends the waiting events of every user at once. Pass `consentDenied: 'skip'` to `startFlow` to skip such events instead (see [Gate a destination with consent](/docs/guides/consent#gate-a-destination-with-consent) and [consent-denied events on a server](/docs/collector#consent-denied-events-on-a-server)).

## Hashing

The destination SHA-256 hashes these `user_data` keys before sending: `em`, `ph`, `fn`, `ln`, `db`, `ge`, `ct`, `st`, `zp`, `country`, `external_id` and `hashed_maids`; a list is hashed value by value. Map personal data only to these keys, in `settings.user_data`, or under `user_data` in a rule's `data` or the destination's `config.data`.

- **Every other key is sent in clear text.** `client_ip_address` and `client_user_agent` are sent as mapped, and so is any other key: nothing checks the names under `user_data`, so `email` or `phone` instead of `em` and `ph` reaches Pinterest unhashed. Keys mapped outside `user_data` and `custom_data` are sent at the top level of the event, unhashed.
- **Values are hashed exactly as mapped**, without normalization. Normalize them upstream in the format Pinterest expects, for example the email trimmed and lowercased.

If a value is already hashed, add its key to `doNotHash` and the destination sends it as mapped.
