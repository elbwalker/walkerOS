# Reditus

<PackageLink env="server" github="packages/server/destinations/reditus" npm="@walkeros/server-destination-reditus" status="beta" />

Server-side delivery to [Reditus](https://www.getreditus.com), the affiliate and referral platform: a sign-up or demo of a referred visitor becomes a referral conversion, and a referred customer's payment is credited to the partner.

## Calls

Each rule picks its call with `settings.type`; without it, `settings.type` of the destination applies, else `conversion`.

| Type | Reditus call | Mapped `data` |
|---|---|---|
| `conversion` | `POST /v2/tracking/conversion` | `uid` or `email`, `affiliate_slug` (the partner's slug from the link: `?red=john` gives `john`) or `advocate_slug`, optional `gr_id` (the Reditus script's cookie, which matches the exact click) |
| `payment` | `POST /v1/payments` | `uid` or `email` (sent as `referral_uid`, `referral_email`), `idempotency_key`, `amount` as an integer in minor units (cents: 99.00 EUR is `9900`), `currency` (lowercased), optional `subscription_id`, `interval` (`month` or `year`), `interval_count` |

An event without what its call needs fails with `missing-input`, and nothing is sent. Without `apiKey`, or with a `type` other than `conversion` or `payment`, the destination does not start, and every push fails with `config`.

Map `idempotency_key` to your payment processor's payment id: Reditus uses it to never credit a payment twice, and a refund in Reditus names the payment by it. If your event carries a decimal price, convert it to minor units in the mapping, for example with [`fn`](/docs/mapping/value#fn).

<CodeSnippet
  code={`"mapping": {
  "user": { "register": { "data": { "map": {
    "uid": "data.id",
    "affiliate_slug": "globals.red",
    "gr_id": "globals.gr_id"
  } } } },
  "subscription": { "start": {
    "settings": { "type": "payment" },
    "data": { "map": {
      "uid": "data.customer",
      "idempotency_key": "data.payment",
      "amount": "data.amount",
      "currency": "data.currency",
      "subscription_id": "data.id"
    } }
  } },
  "*": { "*": { "ignore": true } }
}`}
  language="json"
/>

The `gr_id` cookie and the affiliate slug from the landing URL live in the browser: carry them to the server event (as `globals`, or from your app) so the conversion can be attributed. A visitor who came without a Reditus link has no slug: filter such events with a mapping `condition` instead of letting them fail.

## Personal data

A conversion sends `email`, and a payment `referral_email`, to Reditus in clear, together with `uid` and the `gr_id` cookie value. Reditus matches them as sent and takes no hashed values. To keep emails away from Reditus, map only `uid`, your own customer or account id, as the snippet above does, and use Reditus's UID tracking (see the [Reditus API guide](https://getreditus.com/help/reditus-api)).

## Rate limit

Reditus allows 100 requests every 5 minutes across its API, and each event is one request. The destination does not slow down or hold back requests: a request over the limit fails with the status Reditus answers. Map only the events Reditus needs (the catch-all `ignore` above keeps the rest out), and send payments only for referred customers where you know them.

## Answers that count as delivered

Some Reditus answers outside 2xx mean that nothing needs to be sent. The destination tells them apart by the body Reditus documents for them, so the same status with another body, for example from a wrong `url`, fails:

- `409` "Referral already exists" to a conversion: the referral is there already.
- `400` "idempotency_key has already been taken" to a payment: Reditus has this payment already, for example after a resend from the dead-letter queue.
- `404` "Referral not found" to a payment: Reditus has no referral for this customer and ignores the payment. With the [logger](/docs/collector/logger#log-levels) at `WARN` or lower, the log reports these payments, because a `uid` or `email` mapped from the wrong field gets the same answer.

## Consent

The quickstart sets no `config.consent`, so Reditus receives every event, whatever consent the event carries. To send only events with consent, add `consent: { marketing: true }` to `config`, next to `settings`. An event without that consent is skipped or queued, depending on the collector's `consentDenied`. Server flows built by the CLI skip it and count it in `skipped`. With `startFlow` it waits in the destination's queue by default: a later event that carries consent does not release it, and only a `walker consent` command does, which then sends the waiting events of every user at once. Pass `consentDenied: 'skip'` to `startFlow` to skip such events instead (see [Gate a destination with consent](/docs/guides/consent#gate-a-destination-with-consent) and [consent-denied events on a server](/docs/collector#consent-denied-events-on-a-server)).
