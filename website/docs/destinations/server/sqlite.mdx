# SQLite

<PackageLink env="server" github="packages/server/destinations/sqlite" npm="@walkeros/server-destination-sqlite" status="beta" />

Persists walkerOS events to SQLite. One destination, two drivers behind a single interface: [`better-sqlite3`](https://github.com/WiseLibs/better-sqlite3) for local files (and `:memory:`), and [`@libsql/client`](https://github.com/tursodatabase/libsql-client-ts) for remote Turso / libSQL / sqld over HTTP or WebSocket. Driver selection is URL-driven; both SDKs are optional peer dependencies so you install only the one you need.

The CLI does not install optional peer dependencies, so the bundle contains no
SQLite driver. The destination loads `better-sqlite3` or `@libsql/client` with
Node's module resolution from the bundle's folder, so install the driver there.
Without a driver, init fails with `SQLite driver load failed`.

`schema: "auto"` creates the table at the first push, with the columns listed in [Table columns](#table-columns). Without it, the table has to exist before the first event (see [Setup](#setup)).

<Configuration type="destination" data={data} />

The destination opens the connection during `init()`. The table check and the prepared INSERT run at the first push, so a flow starts without querying the database. With `schema` unset, a missing table fails that push with a `config` error that names `walkeros setup destination.sqlite` (for a rule's `table`, it names the table); with `schema: "manual"` the check is skipped and the push fails with `SQLite prepare failed`. A failed INSERT fails the event with a `transport` error and the event goes to the dead-letter queue ([when delivery fails](/docs/destinations#when-delivery-fails)); a constraint violation (a duplicate under a unique index, a `NOT NULL` column) is marked not retryable. On `destroy()` the connection is closed cleanly. User-provided clients (wired via `env.client` or `settings.sqlite._client`) are left untouched.

## Table columns

Each event is one `INSERT` into these columns. The table that `schema: "auto"` creates has them, plus `id INTEGER PRIMARY KEY AUTOINCREMENT` and `created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP`.

| Column         | Type      | Value                                   |
| -------------- | --------- | --------------------------------------- |
| `timestamp`    | `INTEGER` | `event.timestamp`, epoch milliseconds  |
| `event_id`     | `TEXT`    | `event.id`                              |
| `name`         | `TEXT`    | `event.name`                            |
| `entity`       | `TEXT`    | `event.entity`                          |
| `action`       | `TEXT`    | `event.action`                          |
| `session_id`   | `TEXT`    | `event.user.session`                    |
| `user_id`      | `TEXT`    | `event.user.id`                         |
| `page_url`     | `TEXT`    | `event.source.url`                      |
| `page_title`   | `TEXT`    | `event.data.title`                      |
| `referrer_url` | `TEXT`    | `event.source.referrer`                 |
| `data`         | `TEXT`    | `event.data` as JSON                    |
| `globals`      | `TEXT`    | `event.globals` as JSON                 |
| `consent`      | `TEXT`    | `event.consent` as JSON                 |

A missing text value is an empty string, a missing `data`, `globals` or `consent` is `{}`, and a missing timestamp is the time of the insert. `context`, `custom`, `nested`, `trigger`, `timing`, the other `user` fields and the other `source` fields are not stored, and a mapping's `data` does not change the row.

## Setup

`walkeros setup destination.sqlite` applies pragmas and creates the table and
its indexes when `config.setup` is `true` or an object. When it is omitted or
`false`, the command provisions nothing.

:::caution The default setup table does not fit the insert
By default setup creates one column per event field (`name`, `data`,
`context`, `globals`, `custom`, `user`, `nested`, `consent`, `id`, `trigger`,
`entity`, `action`, `timestamp`, `timing`, `source`), while each event is
inserted into the columns in [Table columns](#table-columns). Every push into
that table fails with `SQLite prepare failed` (the driver reports
`table events has no column named event_id`). Use `schema: "auto"`, or declare
the inserted columns in `setup.schema`.
:::

<CodeSnippet
  code={`"setup": {
  "schema": [
    { "name": "timestamp", "type": "INTEGER" },
    { "name": "event_id", "type": "TEXT" },
    { "name": "name", "type": "TEXT" },
    { "name": "entity", "type": "TEXT" },
    { "name": "action", "type": "TEXT" },
    { "name": "session_id", "type": "TEXT" },
    { "name": "user_id", "type": "TEXT" },
    { "name": "page_url", "type": "TEXT" },
    { "name": "page_title", "type": "TEXT" },
    { "name": "referrer_url", "type": "TEXT" },
    { "name": "data", "type": "TEXT" },
    { "name": "globals", "type": "TEXT" },
    { "name": "consent", "type": "TEXT" }
  ],
  "indexes": [{ "name": "idx_events_name", "columns": ["name"] }]
}`}
  language="json"
/>

Setup applies four pragmas before it creates the table, each overridable in
`setup.pragmas` (for example `{ "journal_mode": "DELETE" }`):

- `journal_mode = WAL` (better concurrent reads)
- `synchronous = NORMAL` (good durability vs. perf balance)
- `foreign_keys = ON`
- `temp_store = MEMORY`

Setup is idempotent: it runs `CREATE TABLE IF NOT EXISTS` and
`CREATE INDEX IF NOT EXISTS`, so re-running it against a populated database
changes nothing. A column that is missing or has another type than declared is
logged as a `setup.drift` warning with the field, the declared and the actual
type. Setup never runs `ALTER TABLE` and never recreates a table.

Use `mapping.settings.table` to route specific events to a dedicated table (for
example orders to `orders`, identities to `identities`). Setup creates only
`settings.sqlite.table`; a rule's table has to exist, or `schema: "auto"`
creates it at its first push. A missing rule table fails its events with a
`config` error.

### `settings.sqlite.schema`

- `"auto"` creates the table, and each rule table, at its first push with the
  columns in [Table columns](#table-columns).
- `"manual"` skips the table check: the table is yours, and init fails with a
  `config` error when `config.mapping` is not set.

Either value logs a WARN at init that points to `config.setup`.

## Drivers

### Local, `better-sqlite3`

Sync native driver, fastest option for single-host deployments. The URL is treated as a filesystem path; `:memory:` works too. All four default pragmas are honored.

<CodeSnippet
  code={`{
  "sqlite": {
    "url": "/var/lib/walkeros/events.db"
  }
}`}
  language="json"
/>

### Remote, `@libsql/client`

Async HTTP/WSS driver for [Turso](https://turso.tech/), self-hosted [sqld](https://github.com/tursodatabase/libsql), or any libSQL-compatible endpoint. Auth via `authToken`. Setup sends the same four pragmas over this driver. Turso Cloud manages journaling itself and does not allow changing the journal mode (see [Turso Cloud limitations](https://docs.turso.tech/cloud/limitations)).

<CodeSnippet
  code={`{
  "sqlite": {
    "url": "libsql://my-db.turso.io",
    "authToken": "$secret.TURSO_TOKEN"
  }
}`}
  language="json"
/>

URL prefixes `libsql://`, `http://`, `https://`, `ws://`, `wss://` route to the libSQL driver. Anything else (bare paths, `:memory:`) routes to `better-sqlite3`.

## Limitations

- Each event is one `INSERT`. The destination has no `pushBatch`, so a `batch` setting has no effect, and the collector logs an ERROR line that names it.
- Nothing resends a failed `INSERT`: the event fails and goes to the dead-letter queue. A failed table check or prepare is tried again at the next push.
