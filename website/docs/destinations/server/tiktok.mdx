## Failures

TikTok can answer HTTP 200 with a non-zero `code` in the body. That counts as a failed push, not as delivered: the event reaches the dead-letter queue and the collector logs one ERROR line. Rate limits and server errors are retryable; other rejections are not. A response outside the 2xx range, a network error, or no answer within 5 seconds fails the event too: the push answers `failed` with the code `transport` (with the HTTP status) or `timeout`. Without `accessToken` or `pixelCode` the destination does not start: every push answers `failed` with the code `config` and the collector logs `destination init failed`. A rule with `silent: true` sends nothing.

## Client IP and user agent

The destination sends the client IP as `context.ip` and the user agent as `context.user_agent` by default. The `ip` and `userAgent` settings resolve against `{ ingest, event }` and default to `["ingest.ip", "event.user.ip"]` and `["ingest.userAgent", "event.user.userAgent"]`, so they fill in whenever the source provides them (see the `config.ingest` recipe on the [Express source](/docs/sources/server/express#ingest-metadata)). A value that resolves to nothing is not sent. Set either setting to `false` to turn it off, or to another mapping value to read it elsewhere.

## Consent

The quickstart sets no `config.consent`, so TikTok receives every event, whatever consent the event carries. To send only events with consent, add `consent: { marketing: true }` to `config`, next to `settings` (with several keys listed, one granted key is enough). An event without that consent is skipped or queued, depending on the collector's `consentDenied`. Server flows built by the CLI skip it and count it in `skipped`. With `startFlow` it waits in the destination's queue by default: a later event that carries consent does not release it, and only a `walker consent` command does, which then sends the waiting events of every user at once. Pass `consentDenied: 'skip'` to `startFlow` to skip such events instead (see [Gate a destination with consent](/docs/guides/consent#gate-a-destination-with-consent) and [consent-denied events on a server](/docs/collector#consent-denied-events-on-a-server)).

## Hashing

The destination SHA-256 hashes three `user_data` keys before sending: `email`, `phone_number` and `external_id`. Map personal data only to these keys, in `settings.user_data`, or under `user_data` in a rule's `data` or the destination's `config.data`.

- **Every other key is sent in clear text.** Nothing checks the key names under `user_data`, so `phone` instead of `phone_number`, or `em` instead of `email`, reaches TikTok unhashed. Keys mapped outside `user_data` are sent in `properties`, unhashed.
- **Values are hashed exactly as mapped**, without normalization. Normalize them upstream in the format TikTok expects, for example the email trimmed and lowercased.
- **Map one value per key.** A list is joined with commas and hashed as one string.

If your data is already hashed or you want to skip hashing for specific fields, use the `doNotHash` setting:

## Deduplication

Each event is sent with `event_id` set to the walkerOS event `id`. If you also run the [TikTok browser pixel](/docs/destinations/web/tiktok), TikTok deduplicates server and browser events that share the same `event_id`, so conversions are not double-counted.
