# LinkedIn Insight Tag

<PackageLink
  env="web"
  github="packages/web/destinations/linkedin"
  npm="@walkeros/web-destination-linkedin"
/>

The [LinkedIn Insight Tag](https://www.linkedin.com/help/lms/answer/a427660)
forwards browser conversions to LinkedIn Campaign Manager for ad optimization,
retargeting, and demographic insights. This destination wraps the standard
Insight Tag snippet (loaded from `snap.licdn.com/li.lms-analytics/insight.min.js`);
there is no npm SDK for the browser tag. Mapped events become
`window.lintrk('track', { conversion_id, conversion_value?, currency?, event_id? })`
calls.

## Opt-in conversion model

LinkedIn is an opt-in conversion platform. Every tracked event must
reference a pre-created Conversion Rule in Campaign Manager via its numeric
`conversion_id`. Events without an explicit `mapping.settings.conversion`
produce zero `lintrk` calls. This is the opposite of analytics destinations
(Amplitude, Clarity, PostHog) which forward every event by default. Map only
the events that matter for attribution.

Events that no rule sends still count as delivered. To report them as skipped
instead, add a wildcard rule with `ignore: true` (`'*': { '*': { ignore: true } }`)
and map the events you want, see [ignore vs silent](/docs/mapping/rule#ignore-vs-skip).

## Falsy guards

The destination protects against misconfigured mappings:

- If `id` resolves to nothing, `0` or a non-numeric string, no `lintrk` call
  is made and the push fails with `missing-input`: the push result lists the
  destination under `failed` and the collector writes an ERROR line. A numeric
  string such as `"67890"` is sent as a number.
- `value` (a number or numeric string), `currency` and `eventId` (non-empty
  strings) are left out of the call when they resolve to anything else. A
  `value` of `0` is sent.

## Consent

LinkedIn is an advertising platform. The walkerOS consent key is **`marketing`**
(not `analytics`):

<CodeSnippet
  code={`config: {
  consent: { marketing: true },
  loadScript: true,
  settings: { apiKey: '123456' },
}`}
  language="typescript"
/>

Until `marketing` is granted, the collector holds the destination's events in
a queue and sends them once consent is granted, see
[consent management](/docs/guides/consent). The Insight Tag itself has no
vendor opt-out API: after a revocation, walkerOS holds new events again, but
the loaded tag stays in the page.

### Deferred script load

With `loadScript: true` and `config.consent`, the Insight Tag loads only after
consent is granted: the destination initializes, and injects the tag, once
`marketing` is granted. walkerOS injects the tag once per page. If your page
already embeds the Insight Tag snippet, leave `loadScript` off (the default):
the destination then only sets the partner ID and, if the page has none yet,
the `lintrk` queue, and sends its calls through the page's tag. With both, the
tag loads twice.

:::note Auto page view + retargeting
The Insight Tag fires its own page view on load and drops first-party cookies
for audience building. The destination has no setting to suppress this. The
page view serves retargeting and is separate from the conversions you map.
:::

## No identity tracking

LinkedIn identity on the web is cookie-based. The Insight Tag manages its
own first-party cookies and matches visitors against LinkedIn member profiles
server-side. There is no `lintrk('identify', ...)` API. The destination does
not forward user IDs, emails, phone numbers, or the `li_fat_id` click ID.

The [server LinkedIn destination](/docs/destinations/server/linkedin) sends
conversions through the Conversions API with `eventId` set to the event's `id`
and can forward `li_fat_id`. Map `eventId: 'id'` here, as in the example above,
to [deduplicate](/docs/destinations/server/linkedin#browser-deduplication)
conversions sent from both.
