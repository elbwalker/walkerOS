[Matomo](https://matomo.org/) is an open-source, privacy-focused web analytics
platform that works self-hosted or in Matomo Cloud. This destination forwards
walkerOS events to Matomo via the `_paq` command queue with support for page
views, custom events, goals, site search, content tracking, and custom
dimensions.

## Installation

<Quickstart data={data} />

The quickstart above sets no consent, so `matomo.js` loads and Matomo receives
every event without `analytics` consent, and a revocation changes nothing. Add
`consent: { analytics: true }` to `config`, next to `settings`, before you go
live (see [gate a destination](/docs/guides/consent#gate-a-destination-with-consent)).

<Configuration type="destination" data={data} />

With `loadScript: true` the destination loads `matomo.js` from `url` and sets
the tracker URL and site id; a missing `siteId` or `url` fails it with a
`config` error. Without `loadScript`, your own Matomo snippet does both.
Commands go onto Matomo's `_paq` queue, which the tracker works through once
it has loaded, so events pushed before that count as sent. If the injected
`matomo.js` fails to load, the pushes after its error fail with
`vendor-not-loaded` and an ERROR line. If no tracker ever loads (no
`loadScript` and no snippet of your own, or a `matomo.js` that neither loads
nor fails), every event counts as sent and none reaches Matomo.

A destination with `config.consent` tells Matomo when its consent changes:
once none of its required keys is granted, it sends `forgetConsentGiven`, which
stops link tracking too, and a grant sends `setConsentGiven`.

## Unmapped events

A page view needs no rule: it sends `trackPageView` with the page title. Any
other event without `rule.name` and without a tracking flag (`siteSearch`,
`contentImpression` or `contentInteraction`) sends only its goal when the rule
has `settings.goalId`, so a goal-only rule needs no name. Without a goal, such
an event fails with `missing-input`; add an `ignore: true` rule for events you
do not send. A rule with `silent: true` sends only its goal, and nothing
without one.

A `goalId` must be a Matomo goal ID, a positive integer like `1` or `"1"`.
Another value is skipped and logs one ERROR line per cause: the event's own
hit goes without the goal, a goal-only rule fails with `missing-input`, and a
`silent: true` rule sends nothing.

## Ecommerce

Matomo needs an `addEcommerceItem` call for each product before a cart update,
and before an order to record the order's products. A product view is
`setEcommerceView` followed by `trackPageView`. A rule sends one command per
event, so the destination cannot send these sequences.

## Custom dimensions

Custom dimensions are keyed by bare dimension id, like
`{ "1": "data.category" }`. Each value is a mapping value, resolved for every
event.

- `settings.customDimensions` applies to every hit.
- A rule's `settings.customDimensions` applies to that rule's hits and wins
  per key. A rule dimension that resolves to nothing removes that dimension
  for the hit, even when the destination sets it.

The dimensions are set with `setCustomDimension` right before the event's
hits, a goal included. After them, rule-only dimensions are deleted with
`deleteCustomDimension` and the destination values are set again, so a rule
value never leaks into later requests such as outlinks or the heart beat. With
destination dimension `1` set to `globals.pagegroup` and a page view rule
dimension `2` set to `data.id`, a page view pushes:

<CodeSnippet
  code={`_paq.push(['setCustomDimension', 1, 'docs']);
_paq.push(['setCustomDimension', 2, '/docs/']);
_paq.push(['trackPageView', 'walkerOS documentation']);
_paq.push(['deleteCustomDimension', 2]);
_paq.push(['setCustomDimension', 1, 'docs']);`}
  language="javascript"
/>
