# TikTok Pixel

<PackageLink
  env="web"
  github="packages/web/destinations/tiktok"
  npm="@walkeros/web-destination-tiktok"
/>

The [TikTok Pixel](https://business-api.tiktok.com/portal/docs?id=1739585702922241)
forwards browser conversions to TikTok Ads for optimization, audience
building, and reporting. This destination loads the TikTok Pixel script from
`analytics.tiktok.com/i18n/pixel/events.js` unless `loadScript` is `false`.
Events become `ttq.track(name, params, { event_id })`
calls; identity becomes `ttq.identify({ email, phone_number, external_id })`;
with `config.consent`, consent toggles `ttq.enableCookie` / `ttq.disableCookie`.

## Installation

<Quickstart data={data} />

The quickstart above sets no consent, so the TikTok Pixel script loads as the
flow starts, every event the destination sends goes out without `marketing`
consent, and a revocation changes nothing. Add
`consent: { marketing: true }` to `config`, next to `settings`, before you go
live (see [Consent](#consent)).

The destination starts only when `window.ttq` already provides `load`. On a
page without that, the quickstart does not start: the console shows one ERROR line
`destination init failed` with the code `vendor-not-ready`, every push answers
`failed` with that code, and each push tries to start it again. Whatever sets
up `window.ttq` on your page runs outside the walkerOS consent gate, so it has
to wait for consent itself; otherwise the Pixel loads before `config.consent`
is met.

## Standard events

TikTok optimizes ads on its
[standard events](https://ads.tiktok.com/help/article/standard-events-parameters).
Use `mapping.name` to send a walkerOS event under one of their names, for
example `ViewContent`, `AddToCart` or `Purchase`; an event without a rule goes
out under its walkerOS name. A rule whose `data` resolves to something other
than an object is sent with empty parameters, and its push answers `done`.

## Advanced matching

TikTok matches conversions back to TikTok users via three optional parameters:
`email`, `phone_number`, `external_id`. The destination passes the resolved
values to `ttq.identify()` as they are, unhashed. TikTok states that its Pixel
hashes email addresses and phone numbers with SHA-256
([Advanced Matching](https://ads.tiktok.com/help/article/advanced-matching-web));
the values still reach TikTok's script in the browser in plain form.

`settings.identify` (destination-level) fires on first push and re-fires only
when the resolved value changes.
`mapping.settings.identify` (per-event) overrides for one push, which is useful
for signup and checkout flows where the identity becomes available mid-session.

`ttq.identify()` always fires before `ttq.track()` so Advanced Matching
is set for the conversion event.

## Consent

For TikTok, an advertising platform, the typical walkerOS consent key is
`marketing` (whatever name your CMP reports). The walkerOS `config.consent`
gate holds events until that consent is granted: they wait in the
destination's queue and are sent once it is, and walkerOS injects the Pixel
script only then (see
[consent management](/docs/guides/consent#gate-a-destination-with-consent)).
The destination's `on('consent')` handler then toggles TikTok's own cookie
state for attribution.

<CodeSnippet
  code={`config: {
  consent: { marketing: true },
  settings: { apiKey: 'C4XXXXXXXXXXXXXXXXXXX' },
}`}
  language="typescript"
/>

The handler acts on a consent command that names at least one key of
`config.consent` and reads the whole consent state: it calls
`ttq.enableCookie()` when at least one of those keys is granted, the rule the
gate applies to events, and `ttq.disableCookie()` when none is.

:::note Page views
The destination calls no `ttq.page()`. A walkerOS `page view` without a rule
goes out as `ttq.track('page view', ...)`.
:::
