# Consent management

Managing user consent is critical for legal compliance and user privacy.
WalkerOS follows a **privacy-by-design** approach and offers multiple ways to
handle consent and manage data processing to ensure the user's privacy is
respected.

:::warning

We don't give any legal advice. Make sure to consult a legal expert to ensure
that your implementation is compliant with the laws and regulations that apply
to your business.

:::

Typically, a Consent Management Platform (CMP) handles the consent. This is an
asynchronous process. The CMP has to be loaded, a user has to make a choice,
and/or the state has to be updated. walkerOS provides
[CMP source packages](/docs/sources/web/cmps) that automate
this. They listen for CMP events and call the consent command for you.

To set/update the consent state, the CMP should actively push the
`consent command` with a group or an individual tool's permission state
(`true/false`). If only one condition applies, consent is granted. Updating only
one value won't override existing states.

<CodeSnippet
  code={`elb('walker consent', { functional: true, marketing: false });`}
  language="javascript"
/>

Consent keys can be defined arbitrarily (typically known as *functional*,
*analytics*, and *marketing*). However, you can also use individual names for
each vendor.

The walker handles the **race conditions**: Previously pushed events get
processed in the correct order after granting the consent state with the
destinations as well as new ones.

### Destinations

With each event, the consent states get checked. Every event will be added to an
ordered queue if consent isn't granted yet. `config.queue` does not switch off
this consent queue. The queue resets with each `walker run` command. And will be
(re-)processed with each `walker consent` update. The key must match the key
used in each `destination.config.consent`.

:::note

Before a queued event is processed:

- `consent` is replaced with the current collector state. Once the event
  passes, it carries only the granted keys.
- `user` is merged with the collector's user data. Values already on the event
  take precedence.
- `globals` keeps the values the event was captured with.

:::

:::note

A destination only requires one granted consent state to process events.

:::

A destination receives the current consent state through its `on('consent')`
handler before any event is sent to it. This holds when consent was set before
or after `walker run`, when the destination waits for consent with `require`,
and when it is added with `walker destination` while the flow is running. The
collector waits for the handler to finish, up to the destination's
`config.timeout` (10 seconds by default). If the handler does not finish in
that time, or fails, the destination receives no events until a later delivery
of the state finishes. Its events wait in its queue meanwhile and are discarded
at the next `walker run`. The collector delivers the state again when it
changes, and with the next event once the timeout has passed.

To revoke consent and stop sharing events with a destination, all matching rules
have to be set to `false`:

<CodeSnippet
  code={`elb('walker consent', { marketing: false });`}
  language="javascript"
/>

## on consent

To run code when consent changes, use the `on consent` command. `rules` is an
object with one handler per consent key:

<CodeSnippet
  code={`// Run code when functional consent changes
elb('walker on', {
type: 'consent',
rules: {
functional: (consent) => {
if (consent.functional) {
// functional consent was granted
}
},
},
});

// Later, a CMP has to update the consent state
elb('walker consent', { functional: true });`}
  language="javascript"
/>

No handler is called before the collector runs. After that, a handler runs when
its key is set at registration or when the collector starts, and each time its
key is part of a `walker consent` command, for a denial as well as a grant. A
bare function as `rules` has no key and is never called.

Do not start walker.js from a consent handler. walker.js starts on load, so a
second `walker run` sends another `page view` and fires every `load` element
again. walker.js leaves consent to your tags, for example in GTM with Consent
Mode. In your own bundle built with `run: false`, call `elb('walker run')` once,
from your CMP's first consent callback, instead, since an `on consent` handler is not called
before the collector runs. Any later `walker run` clears the destination
queues, so events still waiting for consent are lost.

Another example of how to use the `on consent` command might be to update
[Googles consent mode v2](https://developers.google.com/tag-platform/security/guides/consent?consentmode=basic):

<CodeSnippet
  code={`elb('walker on', {
type: 'consent',
rules: {
analytics: (consent) => {
gtag('consent', 'update', {
analytics_storage: consent.analytics ? 'granted' : 'denied',
});
},
marketing: (consent) => {
const state = consent.marketing ? 'granted' : 'denied';
gtag('consent', 'update', {
ad_user_data: state,
ad_personalization: state,
ad_storage: state,
});
},
},
});`}
  language="javascript"
/>

Each Google consent type follows its own walkerOS consent key, and a denial or
a revoked consent sends `denied`.
