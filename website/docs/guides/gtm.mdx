# Use walkerOS events in GTM

[walker.js](/docs/apps/walkerjs) turns `data-elb` attributes into `dataLayer`
pushes. This guide sets up Google Tag Manager to use them: triggers, variables,
GA4 event names and ecommerce items.

## What you get

Every walkerOS event is one push. `event` is the walkerOS event name with its
space (`product view`, `order complete`), and `_clear: true` tells GTM to
replace each key of the push instead of merging it with the previous value, so
no `data.price` leaks from one product into the next. A `product view`, with
the values that change on every push shown as placeholders:

## Where to place the tag

Add the walker.js script tag below the GTM snippet and your Consent Mode
default:

<WalkerjsSnippet />

walker.js starts once the document is parsed and pushes into the same
`dataLayer` array as GTM. If GTM loads later, it processes the earlier pushes in
order when it starts.

When you cannot edit the page, load walker.js from a GTM Custom HTML tag on the
Initialization or All Pages trigger instead. The trade-offs: events start only
after the container has loaded, and a blocker that blocks GTM blocks walker.js
too.

## Trigger

Create a trigger of type **Custom Event** with the event name `product view`.
For several events in one trigger, tick **Use regex matching** and enter
`^product (view|add)$`. The built-in `{{Event}}` variable returns the name with
its space.

## Variables

Create **Data Layer Variables**, version 2, with dot paths:

| Data Layer Variable name | Example value |
| --- | --- |
| `data.name` | `Cotton Tee` |
| `data.price` | `25` |
| `globals.pagetype` | `product` |
| `context.stage.0` | `checkout`: context values are `[value, order]` pairs, `.0` reads the value |
| `user.id` | the id set with `walker user` |
| `nested` | the list of entities inside the tagged element |
| `data` | the whole `data` object, used by the items variables below |

## GA4 event names

walkerOS names are neutral, so map them to GA4 names with a **Lookup Table**
variable. Input `{{Event}}`:

| walkerOS event | GA4 event |
| --- | --- |
| `page view` | `page_view`, and set `send_page_view` to `false` in your Google tag, otherwise every page counts twice |
| `product view` | `view_item` |
| `product add` | `add_to_cart` |
| `order complete` | `purchase` |
| `session start` | not forwarded: `session_start` is a reserved GA4 name |

Use the variable as the event name of one GA4 Event tag, fired by a Custom
Event trigger that matches the walkerOS events in the table.

## Ecommerce items

GA4 expects an `items` array. A product event carries the product in `data`;
an order carries its products in `nested`, when the order element contains
tagged products:

<CodeSnippet
  code={`<div
  data-elb="order"
  data-elb-order="id:0rd3r1d;total:50"
  data-elbaction="load:complete"
>
  <div data-elb="product" data-elb-product="id:tee;name:Cotton Tee;price:25;quantity:2"></div>
</div>`}
  language="html"
/>

Build `items` with a **Custom JavaScript** variable. For a single product, with
a Data Layer Variable named `DLV - data` for the key `data`:

<CodeSnippet
  code={`function () {
  var d = {{DLV - data}} || {};
  return [{
    item_id: d.id,
    item_name: d.name,
    price: d.price,
    quantity: d.quantity || 1
  }];
}`}
  language="javascript"
/>

For an order, with a Data Layer Variable named `DLV - nested` for the key
`nested`:

<CodeSnippet
  code={`function () {
  var nested = {{DLV - nested}} || [];
  var items = [];
  for (var i = 0; i < nested.length; i++) {
    if (nested[i].entity !== 'product') continue;
    var d = nested[i].data || {};
    items.push({
      item_id: d.id,
      item_name: d.name,
      price: d.price,
      quantity: d.quantity || 1
    });
  }
  return items;
}`}
  language="javascript"
/>

Pass the variable as the `items` parameter of the GA4 Event tag. For
`purchase`, add `transaction_id` from `data.id` and `value` from `data.total`.

## Keys that may collide with your own

A walker push can carry these top-level keys: `event`, `_clear`, `name`,
`entity`, `action`, `data`, `context`, `custom`, `globals`, `user`, `consent`,
`nested`, `trigger`, `id`, `timestamp`, `timing` and `source`. With `_clear`,
each key a push carries replaces whatever your site pushed under the same name.

`user` and `consent` are left out of the push while they are empty, for example
`user` until you set one, so a `user` your site pushed stays intact. Every other
key is in every push, `data`, `context`, `custom` and `globals` even when empty,
so `_clear` wipes the previous event's values from GTM's data model.

Names that often appear in hand-written dataLayer specs are `data`, `context`,
`custom`, `id`, `source`, `user` and `consent`. Keep your own values under other
keys, such as `ecommerce` or `page`, which walker.js never pushes.

The reverse holds as well: walker keys stay in GTM's data model after a walker
push, so a variable such as `data.name` returns the last walker value on your
site's own events too. Use walker variables only in tags that walker events
trigger.

## Fields to ignore

`source`, `timing`, `id` (an event id, not your product's `data.id`), `custom`
(extra `elb()` values, usually empty) and `consent` (walkerOS consent state, not
Consent Mode) rarely matter in GTM.
The useful ones are `event`, `entity`, `action`, `data`, `globals`, `context`,
`nested` and `user`.

## Single-page apps

walker.js sends a `page view` for every route change by itself. Do not add a
History Change trigger that calls `elb('walker run')` or fires a GA4 page view:
every navigation would count twice.

## Consent

walker.js sets no cookies, writes no storage, and its events only reach
`window.dataLayer`. Whether a tag may send them on stays your GTM setup's job:
Consent Mode and the consent settings of each tag work as they do today.

## Debug

GTM Preview lists each walkerOS event by name in its timeline, and the Data
Layer tab shows the push. walker.js writes nothing to the console except
errors.

## Need more?

Skip the variables: in the [walkerOS app](https://app.walkeros.io), build your
own bundle that sends the same events to
[GA4 directly](/docs/destinations/web/gtag/ga4), with mapping and consent rules,
in the browser or server-side.
