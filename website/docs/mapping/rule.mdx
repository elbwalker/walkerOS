# Mapping.Rule

A `Mapping.Rule` is the object that sits at
`config.mapping[entity][action]` on a source or destination. It decides whether
an event applies, renames it, reshapes its data, and can
emit side effects (batching, custom settings). The shape is defined in
[`packages/core/src/types/mapping.ts`](https://github.com/elbwalker/walkerOS/blob/main/packages/core/src/types/mapping.ts).

## Configuration

Every value-shaped field (`data`, entries in `policy`, entries in `settings`
that take values) accepts any form documented in
[Mapping.Value](./value.mdx).

## How destinations consume a rule

When an event reaches a destination, the collector picks one rule from
`mapping[entity][action]`, where entity and action are the two words of the
event name. An array means "try each in order, first matching rule wins". A
`'*'` key on the entity or the action level is a wildcard. The lookup tries
four tiers, most specific first:

1. `entity action`, the exact key.
2. `entity *`, the entity's own wildcard action.
3. `* action`, a wildcard entity with the exact action.
4. `* *`, the global wildcard.

The first tier that has a rule whose `condition` passes wins. A tier that has
rules but whose conditions all fail falls through to the next tier, so a
`product *` rule is still used when every `product view` rule fails its
condition.

In this example `product click` has no exact rule, so the second tier wins:
`product *` is used and `* click` is never consulted.

<LiveCode
  language="typescript"
  labelInput="Configuration"
  rowHeight="synced"
  input={`
await getMappingEvent(
  { name: 'product click' },
  {
    product: {
      '*': { name: 'product_interaction' },
    },
    '*': {
      click: { name: 'generic_click' },
    },
  }
);`}
  output={`{
  eventMapping: {
    name: "product_interaction"
  },
  mappingKey: "product *"
}`}

/>

An event that matches no rule is still sent. The destination's `push` receives
it under its own name with no rule (`context.rule` is undefined), and
`context.data` holds only what the destination-level `data` and `include`
produce. What the destination sends for an unmapped event depends on the
destination; its page says. No setting sends only mapped events. To get that,
ignore everything with a catch-all rule and map the events you want:

```typescript
{
  '*': { '*': { ignore: true } },
  order: { complete: { name: 'purchase' } },
}
```

With the catch-all in place, an event whose specific rules all fail their
condition falls through to it and is ignored too.

:::info Mapping wildcards differ from contract wildcards
Mapping wildcards are **first-match**: the lookup above picks one rule and no other rule is consulted. [Contract wildcards](/docs/getting-started/flow/contract#wildcard-inheritance) are **additive**: every matching level merges in. The two systems intentionally pick different defaults: mapping selects a single transformation target, contract accumulates requirements.
:::

A rule's `condition` is checked while matching: the first rule whose
`condition` passes is used; if none passes, the lookup continues with the next
tier. A condition may be async: conditions are awaited one by one, in rule
order. A condition that throws fails the event: it is not treated as no match,
because falling through could send an event the rule meant to stop. The push
answers `ok: false` with the reason `mapping`, and the collector logs one ERROR
line. Once a rule matches, the collector runs `policy` (event-level), resolves
`data`, then hands the result to the destination's `push` (or buffers it when
`batch` is set and the destination batches). A rule-level `consent` is not
checked: gate a destination with `config.consent`, or a single value with a
`consent` entry.

A `policy` entry that resolves to nothing removes the field. That is how a
consent-gated entry redacts a value when consent is denied.

### Batch scheduling

`batch` accepts a number (the debounce `wait` window in ms) or an object
`{ wait?, size?, age? }` for finer control:

- `wait` (ms): debounce window. The timer resets on every push.
- `size`: hard count cap. Flushes immediately at this many events.
- `age` (ms): hard age cap since the first entry of the current window.

A rule-level `batch` splits this entity-action into its own buffer. When the
destination also sets `config.batch`, the rule's values override
destination-level per field (`rule ?? config ?? default`); fields the rule omits
fall back to `config.batch`. Setting `config.batch` alone batches **all** of the
destination's events into one shared buffer with no rule needed. Defaults when
batching is enabled: `size: 1000`, `age: 30000`. When events keep arriving
faster than `wait`, its timer keeps resetting, and the `size` and `age` caps
are what force the flush.

Batching works only on a destination that implements `pushBatch`; its page
says whether it does. On any other destination `batch` has no effect: every
event goes to `push` right away, and the collector logs one ERROR line naming
the `batch` when the destination registers (on inline `code` without
`pushBatch`, `walkeros validate` and the bundle reject it). Pending batches are
flushed when the collector shuts down
([`walker shutdown`](/docs/collector/commands#shutdown), which the runner sends
on exit), waiting up to 5 seconds per batch. In the browser nothing sends
`walker shutdown`; the browser source sends
[`walker flush`](/docs/collector/commands#walker-flush) when the page goes away,
so pending batches are sent then. The
[`pushBatch` contract](/docs/destinations/create-your-own#the-pushbatch-function-optional)
covers what the destination receives.

## Conditional rules

Use an array with conditions to branch by event contents; the first matching
rule wins.

<LiveCode
  language="typescript"
  labelInput="Configuration"
  rowHeight="synced"
  input={`
await getMappingEvent(
  {
    name: 'order complete',
    data: { value: 100 },
  },
  {
    order: {
      complete: [
        {
          condition: (event) => event.data?.value > 50,
          name: 'high_value_purchase',
        },
        { name: 'purchase' },
      ],
    },
  }
);`}
  output={`{
  eventMapping: {
    name: "high_value_purchase"
  },
  mappingKey: "order complete"
}`}
  fn={logEvent}
/>

## Ignore vs silent {#ignore-vs-skip}

Two flags control what a destination does with an event whose rule matched:

- `ignore: true`: the rule matched and the destination's `push()` is **not**
  called, so nothing is sent and the rule's `name` and `data` are not applied.
  What runs before the rule is applied still runs: the destination's `init` on
  its first event, its `before` chain, the destination-level `policy` and
  `data`, and the rule's `policy`. Use for suppression. An ignored event counts
  as a deliberate skip: the push result lists the destination
  neither under `done` nor under `failed`, `status.out` and the destination's
  `count` do not move, and `status.destinations.<id>.skipped` counts the event.
  The collector writes a DEBUG line, and Observe shows a skip with the reason
  `ignored`.
- `silent: true`: the rule matched and the destination's `push()` **is** called
  with the rule. Every destination honours `silent`: `settings.identify`,
  `settings.revenue`, `settings.group`, and other side effects still run and
  only the default forwarding call (e.g. `track()`, `capture()`, `event()`) is
  suppressed. Use for "identify without an event" style flows. A destination
  has no side effect to run for a rule that maps none, so the rule then sends
  nothing and is not a failure.

If both are set on the same rule, `ignore` wins.

`ignore` suppresses one destination. To drop an event before any destination
sees it, use a route `stop` in `collector.next`; to drop it for one destination
by condition, use a `stop` in that destination's `before`. See
[Dropping an event with `stop`](/docs/getting-started/flow/routing#dropping-an-event-with-stop).

<LiveCode
  language="typescript"
  labelInput="Configuration"
  rowHeight="synced"
  input={`
await getMappingEvent(
  { name: 'test event' },
  {
    test: {

    },
  }
);`}

    ignore: true

```typescript
{
  user: {
    login: {
      silent: true,
      settings: { identify: { map: { user: 'data.id' } } },
```

## API reference

The two functions below resolve mappings. Destinations and sources call
them through the collector, but they are exported for direct use in custom
transformers or tests.

### getMappingEvent

```typescript
getMappingEvent(
  event: WalkerOS.PartialEvent,
  mapping?: Mapping.Rules,
  collector?: Collector.Instance,
): Promise<Mapping.Result>
```

Resolves the matching rule for an event based on `event.name` (the
`"entity action"` string), in the lookup order above. Returns
`{ eventMapping, mappingKey }` where `eventMapping` is the matched
`Mapping.Rule` and `mappingKey` is the lookup key that matched (including
wildcards). When no rule matches, `eventMapping` is undefined and `mappingKey`
is an empty string. When there is no mapping, or the event name is a single
word with no action, the result is `{}`. Pass the `collector` when rules have
conditions: it is the conditions' context, and without it a condition gets
none. A condition that throws rejects the call with a `mapping` error.

### getMappingValue

```typescript
getMappingValue(
  value: unknown,
  mapping: Mapping.Data,
  context: Mapping.ValueContext, // { collector, event?, consent? }
): Promise<WalkerOS.Property | undefined>
```

Resolves a `Mapping.Value` against an input. Used internally for every `data`,
`policy`, and `set` resolution. The companion reference for each value form
lives in [Mapping.Value](./value.mdx).

The context requires the running `collector`: inside a step, take it from the
step's context; elsewhere, use the one `startFlow` returns.

```typescript
const { collector } = await startFlow();
await getMappingValue(event, 'data.id', { collector });
```

## Rule-level examples

### Source mapping

Normalize events before they reach the collector. At a source a rule renames
the event (`name`), edits it (`policy`) or drops it (`ignore`); `data`,
`include`, `remove`, `batch`, `settings`, `extend` and `silent` have no effect
there, because only the edited event moves on. `walkeros validate` and the
bundle reject those keys (`MAPPING_NO_OP`), naming the path and what applies at
a source; if such a config still runs, the collector logs one ERROR line when
the source registers, naming each key. A dropped event's push result is
`{ ok: true, dropped: true }`.

<CodeSnippet
  code={`await startFlow({
  sources: {
    browser: {
      code: sourceBrowser,
      config: {
        mapping: {
          product: {
            click: {
              name: 'product view',
              policy: {
                'data.id': { fn: (e) => e.data?.id?.toUpperCase() },
              },
            },
          },
          test: { '*': { ignore: true } },
        },
        policy: {
          'user.email': { fn: (e) => e.user?.email?.toLowerCase() },
        },
      },
    },
  },
});`}
  language="typescript"
/>

### Destination mapping

Transform for a specific destination API:

### Combined flow

The same event can be transformed at both stations:

```text
1. Browser sends: "product click"
2. Source mapping:       "product click" → "product view"
3. Destination mapping:  "product view"  → "view_item"
4. GA4 receives:         "view_item"
```

## Patching package-shipped rules

`@walkeros/transformer-ga4` ships its own default mapping rules. Normally, a
user rule at the same key replaces the default in full. Two keywords change
that:

### `extend` (config layer)

`extend` holds a partial rule that is deep-merged onto the package-shipped
default at the same key instead of replacing it. The merge happens once at
init, before any event is evaluated. A `null` value clears an inherited field.

Use `extend` when you want to add or override one field of a default rule while
inheriting the rest unchanged. Only a package that ships defaults merges
`extend`, so it has an effect in `@walkeros/transformer-ga4`'s
`settings.mapping` only. In any other rule, a destination's own mapping
included, `walkeros validate` and the bundle reject it (`MAPPING_NO_OP`): write
the fields on the rule itself.

### `remove` (output layer)

`remove` is a list of dotted paths stripped from the produced data payload
after evaluation, regardless of how each field was produced (`map`, `fn`,
`include`, etc.). It is applied last, so it always wins.

Use `remove` when you must not emit a field (PII, a vendor-reserved parameter)
but do not want to rewrite the full rule. `remove` works in a destination's own
rules and in `@walkeros/transformer-ga4`'s `settings.mapping`. In a source's or
a transformer's own `mapping` it does nothing, and `walkeros validate` and the
bundle reject it (`MAPPING_NO_OP`).

### Mode switching

A rule that has **neither** `extend` nor `remove` replaces the default in
full. Presence of either keyword activates merge mode for that rule.

### Example: patch a GA4 decoder rule

The transformer-ga4 `purchase` default ships `id`, `currency`, `value`, `tax`,
`shipping`, and `coupon`. The config below adds `affiliation` from a GA4 event
parameter and drops `currency` from the output, keeping all other default
fields:

```json
{
  "settings": {
    "mapping": {
      "purchase": {
        "extend": {
          "data": { "map": { "affiliation": "params.ep.affiliation" } }
        },
        "remove": ["currency"]
      }
    }
  }
}
```

`extend.data.map` is deep-merged onto the default `data.map`, so `affiliation`
is added alongside the existing keys. `remove: ["currency"]` then strips that
field from the final payload.
