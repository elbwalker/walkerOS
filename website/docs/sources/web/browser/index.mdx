# Browser source

Captures user interactions directly from the DOM using `data-elb-*` attributes. Extracts tracking data from markup, tracks pageviews automatically or manually, exposes an enhanced `elb` function with `walker init` support, and provides a trigger system covering click, submit, load, hover, scroll, and visible.

## Enhanced elb

The browser source returns an enhanced `elb` function with additional features:

<CodeSnippet
  code={`// Collector elb: Basic event tracking
collector.push('product view', { id: 'P123' });

// Browser source elb: Enhanced with DOM commands
elb('walker init', document.querySelector('#app'));
elb('product view', { id: 'P123' }); // Also tracks events`}
  language="typescript"
/>

**Browser source elb adds:**

* **DOM commands**: `walker init` for asynchronous DOM element loading
* **Flexible arguments**: support for multiple argument patterns
* **elbLayer integration**: automatic processing of queued commands
* **Element parameters**: support for element parameters in commands

See [Commands](/docs/sources/web/browser/commands) for complete API documentation.

## Single-page apps

With `history: true` the source follows route changes by itself.
[walker.js](/docs/apps/walkerjs) has it on; in your own bundle, set it on the
browser source:

<CodeSnippet
  code={`"browser": {
  "package": "@walkeros/web-source-browser",
  "config": {
    "settings": { "history": true }
  }
}`}
  language="json"
/>

**What counts as a route change.** A `pushState` or a back or forward
navigation that changes the path or the query, and a `replaceState` that
changes the path. A `replaceState` that only rewrites the query (filters, search
boxes) and hash-only changes do not count. Each comparison is against the URL
right before that change.

**What a route change sends.** A new run starts at once: a `page view` for the
URL at the moment of the change, with the previous page view's URL (without its
fragment) as `data.referrer`. `source.referrer` stays the document's referrer,
for attribution. Route changes never start a new session. Every page view after
the first carries the previous URL this way, also when you call
`elb('walker run')` yourself, so a URL redaction rule for personal data in
query strings must cover `data.referrer` too.

**Tagged elements.** A route change does not re-scan the page. The source
watches the document and registers tagged elements whenever they are added, one
task after they appear, so a route's `load` events follow its `page view`. On
the first page load the page's `load` elements fire before the `page view`.

**Migrating.** Remove every route-change `elb('walker run')` call and every GTM
History Change tag that calls it. With `history` on, they make every navigation
send two page views and fire the page's `load` elements again.

**Reused route components.** The source watches added and removed elements, not
attribute changes. A router that reuses a component when only a parameter
changes patches its attributes in place, so its tagged elements do not fire
again. Remount the component per route: React `key={id}`, Vue
`<RouterView :key="route.fullPath">`, Svelte `{#key}`, Next.js `template.tsx`.
Values read with `#innerText` on a reused element do not fire again either.

**Elements that stay across routes** fire `load` and `impression` once per page
load, and their `scroll`, `wait` and `pulse` triggers are not re-armed. A promo
in a persistent layout counts one impression per page load. For per-route
counts, tag elements inside the route's content, or use `visible`.

**Page title, page attributes and globals** are read when the run reaches the
`page view`. Routers that render or set the title later (React Router,
Next.js Pages Router, TanStack Router, Vue with unhead, Nuxt) report the
previous route's values. When you need exact values, keep `history: false` and
call `elb('walker run')` from the router's post-render hook:

| Router | Hook |
| --- | --- |
| React Router | `useLayoutEffect` on `location.key` |
| TanStack Router | `onRendered` |
| Vue Router | `afterEach` plus `nextTick` (title: unhead `dom:rendered`) |
| Nuxt | `page:finish` (title: unhead `dom:rendered`) |
| Angular | `NavigationEnd` plus `afterNextRender` |
| SvelteKit | `afterNavigate` |
| Astro | `astro:page-load` |
| Next.js App Router | no reliable hook |

**Consent.** A destination that waits for consent holds the events from before
the visitor's answer, and every run clears that buffer. A route change is a run,
so when the visitor navigates before answering the banner, the landing page view
is lost, and so is its `session start` unless the session source itself waits
for consent. A multi-page site loses the same when the visitor follows a link.

**One per page.** Run one browser source with `history` on a page.

**Not covered:** hash routers, same-origin iframes, HTML-over-the-wire routers
(Turbo, htmx, Livewire), tagged content rendered later inside shadow roots, and
`data-elbobserve` containers inside shadow roots while `history` is on. Next.js
16 `cacheComponents` reveals cached routes on revisit without adding elements,
so those revisits send a `page view` but no `load` events; use `visible`
instead.

With `history: false` (the default) route changes are not followed,
`data-elbobserve` containers work as before, and `elb('walker run')` re-scans
the page.

## Multiple sources on one page

Any number of browser sources can run on one page. Each keeps its own triggers,
its own element registry, and its own visibility state, so nothing one source
wires, times, or tears down reaches another.

Two page-level resources are the exception, because each is a single slot:

| Resource | Setting | Rule |
|----------|---------|------|
| The writer installed at `window[elb]` | `elb` | The first source to install the name keeps it. |
| The command queue at `window[elbLayer]` | `elbLayer` | The first source to adopt the array keeps it. |

A source that asks for a name another source already holds is refused that one
resource and logs an error. Everything else keeps working: its scope is still
scanned, its triggers still fire, and its own `push` still resolves. A page's
own bootstrap, the `elb` stub function and pre-filled `elbLayer` array defined
before the source loads, belongs to no source and is adopted as usual.

The DOM is not owned. Any number of sources may scan the same node, `document`
included. That is how two flows run on one page: give each its own `elb` name
and its own `elbLayer` name (or `false`), and let them share the markup.

### A vendor flow beside the page's own

Distinct names on both single-slot resources mean nothing is refused on either
side. `pageview: false` leaves the `page view` event to the walker the page
already runs, and the scope narrows the vendor's delegation to the subtree it
cares about.

<CodeSnippet
  code={`import { startFlow } from '@walkeros/collector';
import { sourceBrowser } from '@walkeros/web-source-browser';

const { collector, elb } = await startFlow({
  sources: {
    browser: {
      code: sourceBrowser,
      config: {
        settings: {
          elb: 'vendorElb',
          elbLayer: 'vendorLayer',
          scope: document.body,
          pageview: false,
        },
      },
    },
  },
});`}
  language="typescript"
/>

### An embedded overlay with no window footprint

`elb: false` installs no window property at all and `elbLayer: false` creates no
queue, so the source adds nothing to the page window and reaches its collector
through the `elb` that `startFlow` returns. Pair it with an explicit scope and
the overlay captures only its own markup.

<CodeSnippet
  code={`import { startFlow } from '@walkeros/collector';
import { sourceBrowser } from '@walkeros/web-source-browser';

const host = document.createElement('div');
document.body.appendChild(host);
const overlay = host.attachShadow({ mode: 'closed' });

const { collector, elb } = await startFlow({
  sources: {
    browser: {
      code: sourceBrowser,
      config: {
        settings: {
          elb: false,
          elbLayer: false,
          scope: overlay,
          pageview: false,
        },
      },
    },
  },
});`}
  language="typescript"
/>

### One elbLayer belongs to one walker

A queue is drained once. The source that adopts a named layer reads every entry,
and a command like `walker run` has exactly one addressee, so a second source on
the same array would starve the first rather than join it. Parallel flows use
separate layer names or `elbLayer: false`, and share instrumentation through the
`data-elb` attributes rather than through a queue.

### Overlapping scopes fire once per source

Two sources scanning the same tagged element wire it twice. `click`, `hover`,
`pulse`, `scroll`, `wait`, `impression`, and `visible` each fire once per
source, into that source's own pipeline, and an observed element carries one
dwell timer per source.

The `prefix` setting decides whether that is what you want:

* **Same prefix** is deliberate dual collect. One set of attributes feeds both
  pipelines, and each collector sees the interaction once.
* **Different prefix** isolates the two. Each source only sees elements tagged
  for it, so overlapping scopes cost nothing.

:::note

Give overlapping sources the same scope root. A source discovers
[`data-elbobserve`](/docs/sources/web/browser/tagging/html-attributes#auto-init-with-data-elbobserve)
containers inside its own scope only. When two sources share a prefix and the
container sits outside one of their scopes, only the source that discovered it
reaps elements the container removes. For the other one that element's teardown
never runs: its `pulse` intervals keep firing, its `wait` timeouts stay armed,
and its hover and visibility registrations stay in place against a node that has
left the document, which also keeps that node referenced until the source is
torn down. A shared scope root means both sources see the same containers.

:::

### Known limits

* **Version skew.** A page running an older release of the package leaves no
  ownership mark, so a source injected later reads that layer as free and adopts
  it. This only matters when both use the same layer name, which is what the
  contract above tells parallel flows not to do.
* **The same script included twice.** Each copy scans the same markup into its
  own pipeline, so every event is collected twice. That is a page
  misconfiguration rather than something the source can resolve, and it is
  diagnosable: both refusals log at initialization.
