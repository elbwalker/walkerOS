# Stores

Without stores, each event in a flow is processed in isolation: nothing is shared, cached or persisted between requests. Stores add a shared memory layer that any component in your flow (sources, transformers, destinations) can read from and write to.

A common use is serving the walker.js script from your own infrastructure. The file lives in a store (S3 or filesystem) with `file: true`, and a transformer reads it on each request, so no path is hardcoded and swapping the file needs no rebuild.

Stores hold one canonical value type: structured data, with binary as a first-class leaf. A shared core codec serializes that value to and from each backing. By default a store is a structured key-value store (sessions, lookups, cached responses). Set `file: true` on a byte-native backend (filesystem, S3, GCS) to make it persist raw bytes byte-exact instead, the mode for serving assets such as walker.js. The Sheets store is structured-only and rejects `file: true`. The `file` flag is documented in the [Configuration](#configuration) table below.

## When stores are active

Stores are initialized before any other component in the flow. Once running, they're available to sources, transformers and destinations via `$store.storeId` wiring. A transformer might cache a processed result; a destination might check a store before making an external API call.

```
Flow startup order:
  1. Stores        ← initialized first
  2. Destinations  ← can reference stores via $store.id
  3. Transformers  ← can reference stores via $store.id
  4. Sources       ← start pushing events
```

On shutdown, sources stop first, then destinations and transformers. Stores are destroyed last, so they stay available while every other component shuts down gracefully. A store declared with `cache` is not destroyed at all (see [Known limitations](./cache.mdx#known-limitations)).

## Choosing a store

| Store | Platform | Persistence | Speed | Best for |
|-------|----------|-------------|-------|----------|
| [**Filesystem**](./server/fs) | Server only | Disk (survives restarts) | Fast (local I/O) | Local dev, Docker with baked-in assets |
| [**S3**](./server/s3) | Server only | Cloud (always available) | Network I/O | Managed deployments, shared assets, hot-swap |
| [**GCS**](./server/gcs) | Server only | Cloud (always available) | Network I/O | Cloud Run / GKE deployments, GCP-native |
| [**Sheets**](./server/sheets) | Server only | Cloud (Google Sheets) | Slow (HTTP, rate-limited) | Demos, prototypes with a spreadsheet UI |

For ephemeral, in-process caching, use the built-in [cache tier](./cache.mdx) on any of the stores above; it needs no separate package.

To read from or write to a store from a step without wiring `$store` and writing `$code:`, use the declarative [`state`](../collector/state) block on a source, transformer, or destination.

## Wiring stores to components

Components reference stores in their `env` configuration. In a bundled `flow.json`, write `$store.storeId`; the CLI resolves it, and references to undefined stores are caught at build time. In integrated mode, put the same store definition object in `stores` and in `env`; the collector replaces it with the initialized store instance at startup (matched by object identity, so a copy does not work).

## Common patterns

Stores are rarely used alone. They work together with transformers for use cases that stateless event processing cannot cover.

| Pattern | Store | Transformer | What it enables |
|---------|-------|-------------|-----------------|
| **Self-hosted tag delivery** | S3 or Filesystem (`file: true`) | [File](/docs/transformers/file) | Serve walker.js and tracking pixels byte-exact from your own infrastructure |
| **Response caching** | Built-in cache tier | [Event cache](/docs/collector/cache) on a step | Deduplicate identical requests, reduce load on downstream analytics APIs |
| **Quota-friendly Sheets lookups** | Sheets + [cache tier](./cache.mdx) | Any transformer | Memoize slow API reads, absorb rate limits via TTL |
| **Local development** | Filesystem | [File](/docs/transformers/file) | Serve assets from disk during development, no S3 credentials needed |

## Available stores

### Filesystem

Local filesystem store for server flows. Reads and writes files relative to a base path with path traversal protection. Good for local development and [container deployments with baked-in assets](/docs/apps/runtime#serving-files).

[Learn more &rarr;](./server/fs)

### S3

S3-compatible object storage. Works with AWS S3, Cloudflare R2, Scaleway, DigitalOcean Spaces, Backblaze B2, MinIO, and any S3-compatible provider. The recommended store for managed cloud deployments.

[Learn more &rarr;](./server/s3)

### GCS

Google Cloud Storage with zero runtime dependencies. Built-in auth supports Application Default Credentials (ADC) on Cloud Run / GKE and explicit service account JSON for non-GCP environments. The recommended store for GCP-native deployments.

[Learn more &rarr;](./server/gcs)

### Sheets

Google Sheets store with zero runtime dependencies. Row-per-key storage using the Sheets v4 REST API. Designed for demos and small prototypes where the spreadsheet is the operator-facing UI. Rate-limited; pair with the [cache tier](./cache.mdx) for any non-trivial throughput.

[Learn more &rarr;](./server/sheets)

## Caching on stores

Wrap any of the stores above with a read-through, write-through cache tier by setting `cache` on the store declaration. The default tier uses the collector's built-in in-memory LRU. Compose multi-tier chains via `cache.store`.

[Learn more &rarr;](./cache.mdx)

## The Store interface

Unlike sources, transformers, and destinations, stores are passive: no event chains, no push functions. Every store implements the same operations:

<CodeSnippet
  code={`interface Store.Instance {
  type: string;
  config: Store.Config;
  get(key: string): StoreValue | undefined | Promise<StoreValue | undefined>;
  set(key: string, value: StoreValue, ttl?: number): void | Promise<void>;
  delete(key: string): void | Promise<void>;
  setup?(context: LifecycleContext): unknown | Promise<unknown>;
  destroy?(context: LifecycleContext): void | Promise<void>;
}`}
  language="typescript"
/>

Stores can be synchronous or asynchronous; the interface supports both. In integrated mode, initialized stores are also exposed on the collector instance:

<CodeSnippet
  code={`collector.stores.assets.set('key', 'value');
const value = await collector.stores.assets.get('key');`}
  language="typescript"
/>

## Failed reads

A read, write or delete that fails (a 403, a 5xx, a network error) throws instead of looking like a missing key, and a stored value that cannot be decoded throws too. A key that is not stored is a normal miss and returns `undefined`. A read through a step's [`state`](../collector/state) block or an [event cache](/docs/collector/cache) treats a failed read as a miss for that event and writes one ERROR line per cause, so a failing store is visible without stopping the flow. A component that calls its `env.store` directly receives the error: a transformer's push fails and is reported as a failed push. The file transformer does not catch a failed read either: its request fails. A path that is a directory is a miss in the filesystem store.

## Setup lifecycle

Stores may implement an optional `setup()` lifecycle for one-time, operator-time provisioning, for example creating an S3 bucket. Setup runs only when an operator explicitly invokes `walkeros setup store.<name>`; the runtime never auto-invokes it. Opt in via `config.setup` in the flow config (`true` or an object).

See [Setup lifecycle](/docs/destinations/create-your-own#setup-lifecycle-optional) for the full concept, and the [walkeros setup CLI command](/docs/apps/cli#setup-command) for the operator-facing command.
