**On AWS, configure nothing.** Attach an IAM role to the runtime (ECS task
role, Lambda execution role, EC2 instance profile, App Runner instance role).
The AWS SDK's default credential chain picks it up, so the flow carries no keys.

**Anywhere else, set `config.credentials`** and back both values with
`$secret` references. Never write a literal key into a flow file.

```json
"config": {
  "settings": { "...": "..." },
  "credentials": {
    "accessKeyId": "$secret.AWS_ACCESS_KEY_ID",
    "secretAccessKey": "$secret.AWS_SECRET_ACCESS_KEY"
  }
}
```

`config.credentials` takes `{ accessKeyId, secretAccessKey, sessionToken? }`,
or the same object as a JSON string. It wins over `settings.config.credentials`,
which wins over the default chain. The shape is checked when the destination
starts, without contacting AWS, and error messages name the field that is wrong,
never its value. Instead of `config.credentials`, the standard
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` environment
variables also work, as does `AWS_PROFILE` with a shared credentials file.

**Kubernetes without keys:** with IAM roles for service accounts (EKS) or any
OIDC web identity setup, set `AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE` in
the container. The default chain exchanges the token for short-lived
credentials, so the flow again carries no keys.

Credentials are loaded on the first delivery, not at start. A missing or wrong
key surfaces as the first failed event, with a message that points at
`config.credentials` or the environment.
